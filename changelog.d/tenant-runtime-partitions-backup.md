- **Tenant backup, restore and offboarding cover every tenant runtime partition** — one registry walk (`TENANT_RUNTIME_PARTITION_ROOTS`) now drives all three. A tenant backup includes the tenant's hybrid-ledger, approval-store, usage and execution-metrics partitions and the partitioned state roots, and its manifest lists them (`tenant_runtime_partitions`) with the audit chain key id (`chain_key_id`), never the key. Tenant offboarding also exports and soft-deletes the pipeline-library-run, autonomy-learning, external-operation and standing-grant partitions (new target kind `tenant_runtime_state`); hearing and discussion-create-request receipts stay out of automatic offboarding (review-required retention) but are included in backups.
- **Restore refuses silent ledger rollbacks and revived grants** — a restore fails before extraction (`[BACKUP_RESTORE_APPEND_ONLY_CONFLICT]`) when the target already holds an append-only partition the archive carries, refuses archives with symlink or hard-link members (`[BACKUP_ARCHIVE_MEMBER_TYPE]`) and targets outside the checkout (`[BACKUP_RESTORE_TARGET_OUTSIDE_REPOSITORY]`). Append-only partitions are extracted into staging first: a torn (unparseable) last line is trimmed, and tenant-ledger chains are verified there when the target holds the same chain key, with every entry required to be HMAC-chained under the manifest's key id (`[BACKUP_RESTORE_LEDGER_DOWNGRADED]` / `[BACKUP_RESTORE_LEDGER_CORRUPT]` leave the target untouched). Otherwise the output reports `deferred_key_mismatch`; set `KYBERION_AUDIT_CHAIN_KEY` to the source key and run `pnpm audit:verify`. On a tenant restore the archive's customer decision invites and standing grants go straight into `<partition>/.restore-quarantine/` and live records are never overwritten, so revoked state cannot come back. Tenant offboarding that leaves a tenant runtime partition behind now reports `status: error` (`[OFFBOARD_PARTITION_LEFTOVER]`). Upgrade note: new tenant backups include these partitions; restoring onto a live tenant that already has ledgers now refuses, so restore into an empty target and reconcile there.
- **Unplaceable mission ids no longer leak payloads into the system ledger** — a record whose mission id no process can place (and that names no tenant) keeps its raw `mission_id` in the system ledger, with `payload_withheld: 'mission_unplaceable'`; neither the payload nor any digest of it is written. Rows written before this change are not rewritten. Chronos runtime remediation records now name the mission's tenant and carry only allow-listed lease metadata, and the secret actuator records `mission_id: 'None'` when its ephemeral mission could not be created.
