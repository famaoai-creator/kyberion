---
category: Changed
---

- **The service-preset TTL cache moved from the flat data vault to the cache floor.** `executeServicePresetCached` now stores entries at `active/shared/cache/<tier>/<tenant|shared>/service-preset/{project/<id>|global}/`. The tenant is the tenant of the admitted binding; a call with no admission uses the tier's `shared` partition. tier-guard and tenant scope protect these partitions, and an entry copied into another partition is never served there.
  - An admitted call caches in the admission's `write_tier`; a differing `tier` option is refused.
  - A project id that is not a valid path segment (for example `acme:p1`) is stored under a deterministic `id-<hash>` segment. Project offboarding does not reach these subtrees; tenant offboarding, the expiry sweep and the 30-day rule remove them.
  - The `@agent/core/data-vault` module and the `data-vault-entry` schema are removed. Use `@agent/core/service-preset-cache` (`fetchWithServicePresetCache` with an explicit `{ tier, tenant?, projectId? }` scope), validated by `service-preset-cache-entry.schema.json`.
  - The janitor deletes entries whose own `expiresAt` passed (`scanServicePresetCache`, audited, counted with the storage floors). The cache floor's 30-day rule stays as a backstop.
  - Offboarding finds service-preset cache data by path (target kind `service_preset_cache_tree`). A tenant offboarding exports and soft-deletes `cache/<tier>/<tenant>/service-preset/`. A project offboarding removes the project's subtree from its filter tenant's partition. Without a filter it removes the untenanted subtree plus the subtree of the single tenant the project's lineage resolves to, and refuses with `PROJECT_SERVICE_PRESET_CACHE_AMBIGUOUS` when a tenant partition holds the project but the lineage names no tenant or several. Key-based vault attribution and `PROJECT_DATA_VAULT_AMBIGUOUS` are gone.
  - `active/shared/data-vault/` is now a legacy retention entry, and nothing writes there. The janitor (`scanLegacyDataVault`, which replaces `scanDataVault`) deletes leftover files 30 days after their last write and audits each deletion. Until then offboarding still claims leftover entries that a tenant-admitted call wrote (target kind `legacy_data_vault_entry`): a tenant offboarding claims the tenant's entries, and a project offboarding claims the project's entries for its filter tenant or its single lineage tenant, failing closed like the cache. Unadmitted entries are shared, so the old match on "projectId equals the tenant slug" is dropped. The legacy entry, its sweep, the legacy offboarding claim and the `run_pipeline` / `run_super_pipeline` data-vault grants will be removed together once deployments no longer have the directory.
