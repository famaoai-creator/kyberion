- **tier-guard asks live store grants through one sealed registry instead of importing every capability module (G3, first step)** — each store grant module (DOT results, Discussion requests, customer decision invites / consumer locks / milestones, task source workspaces, PR publication, autonomy learning, pipeline journals, credential material, memory provenance, person charters, personal approval owner windows, Concierge management) registers its own authorization, narrowing, content-check and structural-mkdir rules when it loads; `tier-guard-store-grants.ts` and `customer-decision-write-content.ts` are gone. A grant can only be live once its module has loaded, so an unregistered rule answers exactly as "no grant"; rules that must hold regardless (deny-only role narrowings, the personal approval owner partition) stay in the guard and fail closed when nothing is registered. Registration is sealed (fixed ids, once each, only the grant modules may register — import boundary test). Decisions are unchanged, refusal wording included (old/new matrices over nine stores). `secure-io` now loads 53 core modules at runtime instead of 69. G3 stopped at its rethink conditions: at least eight remaining store roles are cross-store readers, multi-store workflows or deny-only narrowings rather than grants, and `secure-io` stays above 50 while those narrowings must remain in the guard (design doc).
