category: Changed
---

- **One operator identity for terminal approvals** — CLI and script approval requests (provider attestation, project trust, external hooks, secret introduction, mission scope-approve and reconcile-work, organization decisions, entity-governance cleanup, audit-mirror reconcile, third-party `pnpm plugin:install`, service recordings) and `pnpm kyberion approvals --approve` / `pnpm kyberion approve` now record the local owner member as `user:<member_id>` on both sides, with the onboarding name kept in `requestedByDisplayName` / `decidedByDisplayName`. The mission brief page records the same principal. A CLI run inside an agent session (Kyberion agent runtime, or a provider CLI such as Claude Code) opens requests as `agent:<name>`. The detected principal is always kept in `requestedByContext.actorId`; `--requested-by` only adds an identity. With separation of duties on, a terminal without an owner member, or an approval typed inside an agent session, stops with a diagnostic; `pnpm organization member ensure-owner` provisions the owner member. With the setting off nothing new is refused.
- **Terminal approvals under separation of duties need an interactive confirmation** — with separation of duties on, `pnpm kyberion approvals --approve`, `pnpm kyberion approve` and `service_recording review --approve` require an interactive terminal and a typed one-time code printed with the request summary (recorded as `decidedVia: cli_tty_challenge`); without a TTY they refuse and point at Chronos or presence-studio. This is best effort: an agent driving a PTY can answer it, and agent-session markers are advisory. Authenticated surfaces remain the strong path. With the setting off, a decision typed in an agent session is recorded as `caller_supplied` with the agent principal, so it fails a later separation-of-duties re-check.
- **Revoke an approval** — `pnpm kyberion approvals --revoke <id> [--reason "..."]` revokes an approved request: further uses are refused whatever the separation-of-duties setting (an effect that already happened is not undone). Allowed for its requester, an approver, or the local owner (resolved server-side); audited. One-shot effects without an apply claim (service recording promotion, organization decisions) now record that they consumed the approval, so it is used once and a later revoke reports it consumed. Separation-of-duties refusals name the revoke command.
- **Service recording reviews go through the approval store** — `service_recording capture` opens a review request (also `service_recording request-review --recording <path>`), `review --approve|--reject` decides it in the store (separation of duties, audit) and records `review.approval_request_id`, and promotion re-checks and consumes that approval. A review written before this change promotes only while separation of duties is off.
- **`pnpm plugin:install` resolves its approval requester only when it opens a request**, so an official plugin installs with separation of duties on even without an owner member.
