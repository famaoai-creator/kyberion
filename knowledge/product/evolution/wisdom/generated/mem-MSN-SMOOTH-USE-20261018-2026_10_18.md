# Existence audits must not confuse tenant-invisible with missing

A baseline-check NHI orphan scan flagged identities whose affiliated mission existed in another tenant partition. Audits that decide whether a scope is GONE must treat OWNER_NOT_VISIBLE/OWNER_AMBIGUOUS as existing, and a tenant-bound scan may only accuse a miss it can enumerate.

## Hint Scope

mission

## Trigger Phrases

- When auditing whether an affiliation scope still exists (e.g. the L9 NHI orphan check), use existence semantics, not read semantics. A strict lookup refusal of OWNER_NOT_VISIBLE or OWNER_AMBIGUOUS proves the owner directory is on disk — the scope is intact, just outside this processs tenant view, so it is never evidence of a missed offboarding. Only a null/absent result or OWNER_NOT_FOUND counts as missing, and even that is decidable only when the scan covers every place the scope could live: an unbound scan sees all partitions, while a tenant-bound one may only accuse when the affiliation pins the bound tenant. Helper: missionScopeMissing in libs/core/mission-lookup.ts. The same review surfaced two CLI contracts worth repeating: --help on any script must print usage and exit 0 before any side effects (pnpm scheduler --help used to launch the daemon; pnpm knowledge --help exited 1), and operator-facing summaries must print real paths, not placeholders (scenario runner printed a literal <run-id>).
