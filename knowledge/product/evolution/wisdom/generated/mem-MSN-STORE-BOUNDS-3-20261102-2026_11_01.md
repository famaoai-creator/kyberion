# Rotating hash-chained ledgers safely, narrow capabilities for rewrites, one lock per store

Segment rotation must keep truncation detectable (signed archive receipts written before the move; unproven anchors are findings); reserve chain-structure entry types; name and archive segments in chain order; narrow store capabilities can admit a rewrite via exact prefixes; every rewriter takes the same store lock.

## Hint Scope

mission

## Trigger Phrases

- In MSN-STORE-BOUNDS-3-20261102 the last unbounded stores were closed: the hash-chained system and tenant audit ledgers now rotate into segments, the iMessage log rotates with a 90-day archive, tenant autonomy-outcomes partitions are trimmed under a narrowly widened store capability, and a governed CLI recovers leftover compaction copies.

Rules learned:

- Rotating a hash chain must keep truncation detectable. Opening each new file with a signed marker that links to the previous segment's last hash keeps the chain continuous, but it also makes every later segment a valid starting point: deleting the oldest segments then passes verification. A chain may start at a marker only with tamper-evident proof that the missing predecessor was archived legitimately (a signed archive receipt appended to the live chain); without it verification must report an unproven anchor, and restore must refuse it. Stores that code never archives (tenant ledgers) treat any anchored start as a finding.
- Write the proof before the irreversible step. The janitor writes the archive receipt before it moves a segment: a receipt for a segment that is still present is inert, while a move whose receipt then fails leaves a permanent false alarm no later sweep can repair.
- Reserve chain-structure entry types. A generic record(type, data) API let any caller mint an archive receipt; structural types (segment opened, segment archived) must be rejected there and accepted by verify only on the chain that can legitimately carry them.
- Segment names must sort in chain order forever: pick the newest stamp's suffix + 1, never the first free name, and archive strictly oldest-first in chain order (stop at the first unexpired, never the newest), not by per-file mtime.
- Narrow capabilities can admit a rewrite: give the store capability an exact prefix list for that store's own rewrite siblings and archive files one level deep (no mkdir beyond the declared archive dir, other capabilities may not carry prefixes), and take the lock and write the retention audit outside the capability under the caller's identity.
- A writer that cannot write the shared retention audit log must route RETENTION_* records to the audit chain instead of silently dropping them.
- Every party that rewrites a store must take the same lock: write-time maintenance, the janitor and recovery all take the store lock, and recovery also takes the writer's own compaction lock where one exists (dot wake ledger, agent-input-queue, work-coordination fence).
- Side effects reach other callers of a shared writer: rotating in _writeToLedger also rotated mission evidence ledgers nobody reads as segments; scope rotation to the ledgers whose readers handle segments.
