# An append-only store must never be able to block its own repair, and a heartbeat must not report health before work succeeds

Scheduled jobs stopped for two weeks because the trigger journal outgrew a hard read cap that its key-based compaction could never get under, while the heartbeat still looked fresh.

## Hint Scope

mission

## Trigger Phrases

- In MSN-OPS-HEALTH-20261101 every scheduled pipeline (backups, janitor, drills) had stopped since 2026-10-18. libs/core/trigger-runner.ts read the whole trigger-deliveries.jsonl with a 5 MB cap and compacted by keeping the latest record per idempotency key; nearly every key was unique (per-minute cron and watchdog keys), so compaction freed nothing, the file passed 5 MB, every read threw and chronos crash-looped. The janitor that rotates the journal only runs through chronos, so the failure was self-sustaining.

Rules that came out of it:

- Readers of append-only journals never fail on size; compaction is by age (retention window), never only by key; and a read failure degrades instead of crashing the daemon. (The original "hard append cap below a fixed read window" rule is superseded by mem-MSN-STORE-BOUNDS-20261101-2026_11_01: purpose-specific size-independent readers, write-time retention, growth warns.)
- Repair for a runtime store must not depend on the component the store can break. Provide an operator escape hatch (approval-gated rotate) and surface size before the cap.
- A heartbeat written at tick start reports health during a crash loop. Write healthy only after a tick completes, refresh with an in-progress phase during long ticks, and track restarts.
- Fleet-wide 'something ran in 24h' hides per-schedule outages; evaluate overdue and failing per schedule.
- Idempotency keys minted per minute for a recurring condition (watchdog recovery) bloat the journal; key per episode with bounded retries.
