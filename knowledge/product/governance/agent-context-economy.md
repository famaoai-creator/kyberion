# 文脈の経済

長時間セッションのトークン消費は **「文脈サイズ × ターン数」** で決まる。
出力の長さはほぼ効かない。この文書は実測から導いた規則である。

## 実測の根拠（2026-08-19 / 単一セッション）

| 指標                    | 値                             |
| ----------------------- | ------------------------------ |
| assistant ターン数      | 2,411                          |
| 出力トークン            | 2,710,685（平均 1,124/ターン） |
| **cache_read トークン** | **1,087,682,494**              |
| ツール出力の総量        | 2,779,280 文字                 |

文脈の伸び: 序盤 273k → 中盤 **627k** → 終盤 354k（圧縮後）tok/ターン。

**中盤では1ターン進めるだけで63万トークンを再読込していた。** 支配項はこれである。

ツール別のツール出力量:

| ツール   | 件数   | 合計文字                   | 平均       |
| -------- | ------ | -------------------------- | ---------- |
| **Read** | **60** | **1,409,173（全体の51%）** | **23,486** |
| Bash     | 997    | 1,197,821                  | 1,201      |
| Edit     | 139    | 26,937                     | 193        |

出力の大きい上位12件は**すべて自分が書いた中間ファイルの読み戻し**（計約117万文字）だった。

## 規則

### 1. 自分が書いた中間ファイルを読み返さない

最大の無駄。HTMLのバックアップ、JSONダンプ、抽出結果を `Read` で丸ごと戻すのではなく、
`python3 -c` / `grep` / `sed` で**処理して答えだけを取り出す**。

- ❌ `Read scratchpad/data.json`（23,000文字が文脈に入る）
- ⭕ `python3 -c "import json;d=json.load(open('...'));print(len(d), d[0]['id'])"`（200文字）

### 2. 巨大Readのコストは「その場」ではない

23,000文字を入れた時点で残りターンが1,000あれば、**それは1,000回再読込される**。
1回のReadの判断は、セッション全体への課金だと考える。

**判定**: このファイル全文が、これ以降ずっと文脈に残る価値があるか。
無ければ範囲読み（`sed -n 'A,Bp'` / Read の offset+limit）か grep に置き換える。

### 3. 独立した確認は1回の呼び出しにまとめる

「次に何を見るか」が前の結果に依存しないなら、同じ Bash 呼び出しに入れる。
探索中に単発 grep を連発すると、1件あたり数百文字の情報のために
1ターン分（中盤なら60万トークン）を払う。

実測: Bash 997件のうち **64件（4.8%）が実質空振り**。

### 4. 読む量が多く結論だけ要る作業は委任する

サブエージェントのツール出力は自分の文脈に入らない。**判断基準は「読む量」**。

実測: 3エージェント / 306,102 subagent tokens で約180のツール呼び出しを外に出した。
自分の文脈で1ターン60万トークンなら、委任の方が桁で安い。

向くもの: 一覧の機械的な登録、証拠の有無の調査、限定されたコード修正。
向かないもの: 判断そのもの、文脈依存の設計、ユーザーとの合意が必要なこと。

### 5. dist経由のCLIを叩く前にビルドする

`libs/core/*.ts` を直したあと `pnpm <cli>` を叩くと、CLIは `dist/` を見るため
**変更が効いていない状態で挙動を診断してしまう**。手順は
`typecheck → pnpm --filter @agent/core run build → pnpm build:repo → CLI で確認`。

実測: 忘れて2回、各3〜5ターンを再診断に費やした。

### 6. シェル初期化ノイズを消す

非対話シェルで `compinit` が失敗すると、**全Bash呼び出しに3行のノイズが付く**。
1件100文字でも985件で約98,500文字、しかも累積再読込される。

```
not interactive and can't open terminal
compinit: initialization aborted
complete:13: command not found: compdef
```

**発生源の特定を間違えやすい。** エージェントのシェルは
**非対話ログインシェル**（`interactive: OFF` / `login: ON`）なので、
**`.zshrc` は読まれない**。読まれるのは `.zshenv` / `.zprofile` / `.zlogin` である。
判定はこれで確認する。

```bash
echo "interactive: $([[ -o interactive ]] && echo ON || echo OFF)"
echo "tty: $([ -t 0 ] && echo YES || echo NO)"
echo "login: $([[ -o login ]] && echo ON || echo OFF)"
```

このマシンでの実際の原因は `~/.zprofile` が読み込む **nvm の `bash_completion`** だった。
zsh で読まれると内部で `compinit` を呼び、tty が無いためプロンプトを出せずに失敗する。
補完の読み込みに `[ -t 0 ]` を足して解決した（2026-08-19 適用済み）。

**補完はターミナルが無ければ意味がない**ので、この種の行はすべて tty 条件を付けてよい。
ただし**環境変数の export は絶対にガードしない** — `PATH` や証明書パスが渡らず、
コマンド実行そのものが壊れる。**ユーザーのdotfileなので許可を取り、バックアップを取ってから触る。**

### 7. 拒否されうる形でコマンドを投げない

`env` の単独実行、`find` の広域走査、複合コマンドへの混入は権限確認で止まる。
止まると1ターンが無駄になる。実測17件。
サンドボックス依存の操作は**最初から承認前提で1つずつ**投げる。

## やっても効かないこと

- **出力を短くする** — 実測で平均1,124トークン/ターン。支配項ではない。
  短くして情報を落とすと、確認のための追加ターンが発生してかえって高くつく。
- **ツール呼び出し回数だけを減らす** — Bash 997件の合計は120万文字（平均1,201）。
  回数より**1件あたりの出力量**が効く。
