# 受信と実行権限を分離する自律ループ

人間は委任の範囲と最終責任を引き受け、AI はその範囲内で受信から結果の確認まで進める。承認の単位は「AI が考え始めること」ではなく、実際に行使する権限に置く。企業・金融向けの運用設計として監査可能性を確保するための枠組みであり、個別法令への適合を保証するものではない。

## 同じループで扱う三つの境界

1. **受信・整理**: dots がイベントを受け、分類し、分割した作業を WorkItem に登録する。計画の文章に送信・支払いが登場しても、その操作を実行したことにはならない。tenant と有効な DotCharter、件数・費用等の既存制限を満たす通常の intake は、人間への都度確認を必要としない。
2. **作業の開始**: 分類結果に応じて task / mission / pipeline 等の既存実行形態へ接続する。mission の standing mandate は、指定 ID・tenant・有効期限・対象・予算・予定する操作の構造化された範囲を検証する。mission 開始の許可は外部操作の許可ではない。
3. **実操作**: 実際のツール境界で、現在のルール・承認または委任・予算を再検証する。操作と入力、tenant、実行主体、元の作業、現在の責任憲章に束縛した許可だけを利用する。モデルの説明や WorkItem の登録だけから権限は得られない。

dots の能力は実際の runner によって異なる。ToolUse を持たない経路は受信・提案・登録に限定する。ツール利用可能な経路でも、宣言したロールと実行先の認可を維持する。診断や continuous work 等の既存の人間承認境界を、通常 intake の緩和によって解除してはならない。

CLI へのテキスト委任では、実際に選ばれる候補ごとに既存の planner 権限設定と読み取り専用 sandbox を適用する。読み取り・計画専用を投影できない候補は、フォールバック先も含めて起動しない。`advisory` というプロンプトだけを OS 上の実行禁止の証明にしない。

## 設定する責任と拡張点

- `dot-execution-policy.json`: intake の対象形態・件数と Dot の学習条件。
- DotCharter: 担当範囲・ロール・制限。責任憲章の参照を指定した場合は、同一 tenant の現在有効な承認済み憲章と一致させる。参照の省略は外部操作への委任を意味しない。
- standing mandates: mission 開始についての明示的な委任範囲。従来の shadow 評価と実行権限を区別する。
- accountability charter と操作マッピング: 実際の入力から評価事実を導出し、外部実行を許可する範囲を設定する。未対応の操作や不明な評価事実は人間承認へ戻す。任意コードを設定に埋め込んで新たな権限を作らない。

既存の precheck / floor contributor / decision relaxer はこの境界を保って利用する。認可の判定が例外で失敗した場合に、許可とみなして処理を続けてはならない。

## 人間が見るものと残す証跡

人間には承認が必要な実操作と不足する権限を提示する。mission admission を人間承認の根拠にする場合は、構造化した委任 ID・対象・費用・予定操作も承認内容に含め、その変更で承認を無効にする。承認待ちでも、新しいイベントの受信と作業候補の可視化は続けられる。

監査では「受信 → 分類・登録 → 作業の所有者 → 認可の根拠と版 → 実操作の試行 → 結果」を辿れることを確認する。許可・キュー登録・mission 開始は、副作用の成功証拠ではない。学習による権限拡張は、同一 tenant の検証済みの異なる実行結果だけを根拠とする。

機密値を含み得る操作・接続設定のフィンガープリントには、既存の永続監査鍵で用途を分離した HMAC を使う。鍵の更新は古い許可を無効にする。一方、重複実行を防ぐ実行 ID は非機密の作業識別情報だけから作り、鍵の更新でも変えない。

書き込みの結果が不明な場合は、成功にも未実行にも分類せず照合を待つ。汎用サービス経路で同じ書き込みを自動再試行したり、別の transport に切り替えたりしない。冪等性フラグだけでは安全な再実行の証明にならない。支払い等は専用の冪等性・予約・照合手順を利用する。

責任者の稼働状態が取得できない新しい委任経路では、安全モードを適用する。可逆・費用ゼロの内部操作以外を自動実行するには、信頼できる実行ホストから責任者または代理者の稼働状態を供給する。モデルの入力で「在席」を宣言してはならない。

通常の library pipeline は、保護された tenant 別 journal に元の入力・ソースのハッシュ・完了ノードを保持し、人間の承認または却下から同じ試行を続行する。承認した操作には既存の一度限りの apply claim を付ける。ネストした子 pipeline 内で人間待ちになった場合は、親を成功扱いにせず依存関係の確認待ちに止める。子の待機を親全体の再実行許可と解釈しない。
