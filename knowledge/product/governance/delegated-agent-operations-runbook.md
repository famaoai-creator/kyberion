# Delegated agent operations

How to stand up a tenant organization whose routine work runs through
registered agent identities (NHIs) under human-signed charters — the
"one-person company" operating model. Every step goes through governed
facades; never edit `active/organizations/` state by hand.

## Identity model

- **NHI** (`kyberion://agent/<org>/<slug>`): a durable, accountable member of
  the organization. Charter grants bind to it; audit attributes actions to
  it. Register via `pnpm organization agent issue` / `agent activate`.
- **Provider CLI** (devin / claude / codex / …): the execution substrate an
  NHI invokes. Not an org member; appears in the audit trail as a
  delegation-chain hop, never as the accountable actor.
- **Human** (`user:<member-id>`): accountable human and final approver.
  `human_only` decisions cannot be approved from an agent session — run the
  approval command in a human terminal.

## 1. Register the operating NHI

```bash
pnpm scope use --tier confidential --tenant <tenant> --organization <org>
pnpm organization agent issue --slug <slug> --kind agent \
  --display-name "<name>" --accountable-human user:owner \
  --provider-hint <cli> --reason "<why>" \
  --tier confidential --tenant <tenant> --organization-id <org> --apply
pnpm organization agent activate --nhi-id kyberion://agent/<org>/<slug> \
  --expected-version <version-from-issue> --reason "<why>" \
  --tier confidential --tenant <tenant> --organization-id <org> --apply
pnpm organization participant assign --actor kyberion://agent/<org>/<slug> \
  --role implementer --role reviewer \
  --tier confidential --tenant <tenant> --organization-id <org> --apply
```

## 2. Capability control (what each role can do)

- Team-role → KD-05 tier map lives in
  `libs/core/subagent-capability-profiles.ts` (`TEAM_ROLE_CAPABILITY_PROFILE`)
  — reviewer/tester→explorer (read-only), implementer→implementer,
  coordination roles→planner (no tools). Unknown roles fall back to the
  read-only tier.
- Dispatch resolves `resolveDelegationCapabilityProfile(teamRole, purpose)`:
  the _narrower_ of the two bounds wins.
- `assertProviderCanProjectProfile` refuses (fail-closed) a selected provider
  that cannot project the tier — e.g. `codex`/`devin`/`agy` × `planner` have
  refused cells in `reasoning-providers/*.json` `cli.permission_profiles`.
- Effect-level bounds ("deploy-to-prod only", "this data source only") reuse
  existing primitives: authority-role `allowed_actuators`/`write_scopes`,
  Operation `automation_boundary`, charter `external_operations` exact grants,
  `information_flow`. No schema additions needed.

## 3. Delegating provider attestation (tenant:attest_provider)

The grant covers ONE exact claim — `{tenant_slug, provider, training_use:
'none', plan, basis, attested_by}`. Any field change falls back to per-request
human approval.

```bash
# Plan JSON (grants array + expires_at ≤ 365 days)
pnpm onboarding authority preview \
  --file <plan.json> --scope organization --tenant <tenant> \
  --out knowledge/personal/<name>-preview.json   # must be under the active personal profile
pnpm onboarding authority request \
  --file knowledge/personal/<name>-preview.json \
  --scope organization --tenant <tenant>
pnpm kyberion approvals --approve <request-id>   # human terminal
pnpm onboarding authority apply --scope organization --tenant <tenant> --request-id <request-id>
```

Friction points observed:

- **`request` consumes the preview _envelope_** (`input` + `digest` +
  `base_hash`), not the plan. The digest binds the statement to the requesting
  identity — preview and request must run as the same principal. An envelope
  generated by an agent session (`Initiated by: agent:…`) will fail
  `review changed; preview again` when a human requests it; generate your own.
- **`--out` is required** to persist the envelope and must point inside
  `resolveActiveProfileRoot()` (`knowledge/personal/`).
- Stale `libs/core/dist` after switching branches makes preview deny
  "choose at least one exact operation…" — rebuild
  (`pnpm --filter @agent/core run build`) first.

After the grant is installed, `pnpm onboarding llm attest --tenant <t>
--provider <p> --training-use none --plan … --basis … --attested-by …
--apply --accept` executes **without** a human approval request and records
`delegated_via_charter` + `grant_hash` in the audit.

## 4. Routine operations cadence

- Dot charter (`dots/<name>.json`): `operations_cadence` (tick / standup /
  retro). Validate `pnpm kyberion dot validate <id>`, activate
  `dot activate <id>` (already-active is a no-op error).
- Scheduled Operation:
  `pnpm organization operation add --trigger-kind schedule --schedule "<cron>"`
  — the kind is `schedule`, not `cron`. Verify with
  `operation tick --dry-run` then `operation run execute --operation-id <id>`.
- Confidential commands need the tenant bound: `pnpm scope use --tier
confidential --tenant <t> --organization <o>` and/or `KYBERION_TENANT=<t>`.

## 5. PR publication

`pnpm kyberion pr create --title … --body-file …` runs the readiness gate,
the KL-03 knowledge gate, then a **human external-publication approval**.

- Publication artifacts live under
  `active/shared/artifacts/confidential/<tenant>/…`; run pr create with
  `KYBERION_PERSONA=sovereign KYBERION_TENANT=<tenant>` or the artifact-index
  lstat fails with ROLE_VIOLATION.
- After approval, rerun the _same_ command — changed content requires a new
  decision.
- The PR body's `## Coordination` section must carry
  `- Mission ID: MSN-…` for the knowledge gate; resolve every queued
  candidate first (`pnpm kyberion memory promotion-queue`,
  `pnpm mission memory-reject <candidate-id> --tenant-slug <t> --note …
--decided-by user:owner`) or declare it in `## Knowledge`.
- `vcs:pr_create`/`vcs:pr_merge`/`vcs:push` are registry-delegable, but the
  grant binds the _installed NHI in a public execution scope_ — a Devin/CLI
  session (`agent:devin`) is a different actor and still hits the human gate
  by design.

## 6. Mission close-out (direct work)

- `record-evidence <MISSION_ID> <task_id> "<note>" --actor-id <who>` —
  positional task id; a `--task-id` flag is misparsed as the note and the
  task stays `planned`.
- Review-kind tasks need `review-task <MISSION_ID> <task_id> <reviewer>`
  with a reviewer identity **different** from the implementer recorded in
  the execution ledger — a registered NHI works as reviewer.
- Then `verify` → `distill` → `finish`. A failed finish returns the mission
  to `active`; fix and re-run the chain.
