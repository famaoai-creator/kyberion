# A2UI 設定画面の設計と検証

設定画面では、項目を見つけること、編集すること、保存結果を確かめることを一続きに設計する。共通部品を使うだけでは、この流れの品質は保証されない。

## 部品の選び方

- 項目間の移動には `ui:settings-nav` を使う。グループ名、行き先の短い説明、現在位置、必要な項目の未保存表示を与える。本文とメニューの並び順を揃え、保存や診断更新で並びを変えない。
- 本文内の場所へ移動する場合は実際の `href` を渡す。通常のクリックだけを画面の移動処理に接続し、別タブで開く操作や JavaScript がない場合のリンクを保つ。タブとして振る舞わないものに `tablist` を付けない。
- `ui:settings-group` には可能な限り明示的で一意なコンポーネント ID を与える。直接 React から使う場合の自動 ID は補助であり、永続的なリンク先にはしない。
- `ui:setting-row` の `control_id` は単一のラベル付け可能な入力のコンポーネント ID を指す。見えているラベルと入力名が一致し、ラベルのクリックで入力へ移動できることを確認する。複数入力のグループには使わない。補足やエラーは入力部品の `help` / `error` で関連付ける。
- 方針などの長文は `layout: stacked` で編集領域を確保する。画面幅だけでなく、外側のナビゲーションを引いたカードの幅でも配置を切り替える。

## 構成と状態

診断は要約から確認できる形にし、設定本文の入口を押し下げない。狭い画面では現在項目が分かる折りたたみメニューも使える。開閉後の移動は、レイアウトが確定してから対象を測定する。

入力中の状態を下位部品が持つ場合、表示切り替えのために部品をアンマウントすると下書きや確認中の操作が失われる。フォーカス表示、履歴、深いリンク、未保存ガード、保存応答の検証をまとめて回帰確認する。

## 検証と証拠

新部品はカタログ型、JSON Schema、両描画方式、公開エクスポート、日英ギャラリー、テーマの原本を揃える。生成された各画面の CSS は原本から更新する。

React と軽量 HTML の一致テストには、見た目だけでなく `for`、`aria-labelledby`、`aria-describedby`、実際のリンクを含める。長文や保存失敗の状態も使う。

見た目の確認は、実際の外側のレールとヘッダーを含む構成で行う。単独部品の広いキャンバスだけでは中間幅の崩れを確認できない。明暗テーマ、390 / 901 / 1024 / 1440px 程度の幅、長いラベル、キーボードフォーカスを確認する。

静的 HTML の生成成功や DOM の一致は、ブラウザ上の見た目の確認とは区別する。ブラウザ操作が承認ゲートで止まった場合は、その状態を記録し、未確認のスクリーンショットや描画品質を成功として扱わない。
