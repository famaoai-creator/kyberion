# Incident Knowledge Loop: Learning from Failures

## 1. Overview

インシデント（スキル失敗、SLO 違反）を「負の遺産」ではなく「学習の機会」として捉え、自律的に知識を蓄積するためのプロトコル。

## 2. RCA とポストモーテム

進行中の事案には既存の `incident-response`、事後分析には
`incident-analysis-postmortem` を使う。対象の incident、テナント、影響を受けたサービス、
証拠へのアクセス範囲を確定する。障害中は安全確保と復旧を優先し、復旧前後の証跡を残す。

- **証跡と時系列** — ミッションの `evidence/evidence-index.json` に、証跡の出所、観測・取得時刻、スコープ、欠落を記録する。時系列は `evidence/incident-timeline.md` にまとめ、判断時点で観測できた状態と後から判明した事実を区別する。報告に不要な個人情報・秘密は取り除く。
- **因果分析** — 事実、仮説、反証、不明点を分ける。重大事案や複数の制御が関わる事案では CAST を使い、誰または何が判断したか、期待された制御、利用できた情報、応答・受領確認がどこで途切れたかを証跡に紐づける。根本原因を特定できない場合は、残る仮説と追加で必要な証拠を残す。
- **コード実行境界を扱う事案** — 不正なコード実行が疑われる場合、対象の実行境界、権限とデータへの影響、隔離・復旧を確認した証拠を追記する。事前の防御レビューでは STPA-Sec で安全制約を洗い出し、承認失効時の停止や隔離など、防御側の条件を検証する。
- **レビューと対策** — レビュー済みの報告をミッションの `evidence/post-mortem.md` に保存する。対策ごとに担当・期限・観測できる合格条件を決め、WorkItem に関連付ける。担当が未確定ならその旨を明記する。

`incident-post-mortem` パイプラインは分析のドラフトを生成する。対象ミッションを
選んだうえで、レビュー済みの証跡索引と時系列を参照する。担当者がドラフトと証拠を
照合し、ミッションの証跡として記録する。

## 3. 検証と知識化

復旧確認、ポストモーテムの承認、各対策の検証結果を別々に記録する。
未検証の対策は関連 WorkItem で追跡し、回帰テスト、モデル検査、監視、復旧演習などの
結果をもって完了とする。再利用できる知見は、テナント固有の証跡や識別子を持ち出さず、
既存の知識承認・昇格経路で反映する。

RCA は [CAST Handbook](https://psas.scripts.mit.edu/home/get_file4.php?name=CAST_Handbook.pdf)、
事前の防御分析は [STPA-Sec Primer](https://stamp-institute.org/stpa-sec-primer/) を参照する。

## 4. 適用例 — 承認待ちの読み上げを再開できない

この例の根拠は回帰テストで再現した経路。個別の運用事案について人が承認した時刻や
対象 ID は、承認ストアと実行記録を照合して確定する。

| 観点                 | 分析結果                                                                                                                                                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 影響・確認済みの事実 | 実行主体が束縛されていない直接実行では、人の承認が必要と判定されても申請 ID が発行されず、承認・再開に進めなかった。                                                                                                    |
| 途切れた制御         | 実行ゲートは操作を止めた。旧 CLI から申請を起票する境界が呼ばれず、人が判断を返せるフィードバック経路が成立しなかった。                                                                                                 |
| 未確定               | 個別の利用者の申請履歴、発生回数、実機での再生結果。申請 ID が存在する別事案は、承認された操作と再開時の操作の一致を別途確認する。                                                                                      |
| 対策と検証           | 直接 CLI を共通承認ゲートにつなぎ、申請 ID と再開用 ID を返す。隔離した承認ストアで、承認前は実行されない、同じ実行の申請を再利用する、承認後は同じ操作が一度だけ実行される、内容が変われば別申請になることを確認する。 |

証跡は [共通ゲートのモデル検査](../../../libs/core/governance/external-approval-lifecycle.model.test.ts)
と [直接 CLI の承認・再開の統合テスト](../../../scripts/cli/cli-speak-authority.integration.test.ts)。
変更履歴と関連する差分は [PR #1599](https://github.com/famaoai-creator/kyberion/pull/1599) を参照。
