# IPA 不正アクセス漏えい事案 緊急点検チェックリスト (2026-10-09)

IPA「[不正アクセスによる漏えい等の事案を踏まえ、速やかに実施すべき対策等について](https://www.ipa.go.jp/security/security-alert/2026/alert20261009.html)」（2026-10-09 公開）の構造化版。国内の金融機関・通信事業者等で外部公開アプリケーション侵害・アカウント侵害を起点とする大規模漏えいが相次いだことを受けた緊急点検要求。**経営責任としての実施**が求められており、点検・対策の証跡化（coverage ledger / audit chain への記録）を前提とする。

## 判定基準

- 以下の点検で**異常なログまたは異常なアカウント**を発見した場合は、直ちに**セキュリティインシデント**と判定し `../../procedures/system/security-incident-response.md` を開始する。情報漏えいの可能性を考慮し、専門セキュリティベンダーへの詳細調査依頼を強く推奨。
- 異常がなくても §3 の継続対策を適用する。

## 1. 速やかに行うべき点検

### A. 外部公開アプリケーションの精査

| ID  | 点検項目                                                                  | 判定・備考                                                                                                                                                |
| --- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-1 | 自組織が独自に構築・運用する外部公開アプリケーション/サービスの有無を確認 | 全数把握が前提。公開範囲台帳（後述）に登録                                                                                                                |
| A-2 | 各アプリ/サービス単位で直近ログに異常がないか確認                         | 異常の見分け方: エラー出力量、平時との差異。範囲は直近1か月→その後3か月と段階的に拡大。今後の複数回調査に備え「誰がどのように調査できるか」も把握しておく |
| A-3 | 構成要素に未適用の脆弱性対応パッチがないか確認                            | 未適用があれば可能な限り速やかに適用                                                                                                                      |

### B. 利用外部サービスの洗い出し

| ID  | 点検項目                                   | 判定・備考                                                                                                                                                                                                                    |
| --- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B-1 | 利用している外部サービスをすべて洗い出す   | クラウド・VPN等の分類横断、組織全体+部署単位の利用を網羅                                                                                                                                                                      |
| B-2 | サービス単位のログに異常がないか確認       | サービスごとにログ保有期間が異なるため整理が必要。提供者側/利用者側で見えるログも異なる。「誰がいつどのように確認できるか」を整理。判定はログイン失敗量のような分かりやすいものから、ログイン元IP・ログイン時間の平時比較まで |
| B-3 | サービス単位のアカウントに異常がないか確認 | 作ったはずのないアカウントの存在、削除/無効化済みのはずのアカウントの有効化。アカウント操作ログの確認も並行するとより有効                                                                                                     |

### C. 保有データの再点検

| ID  | 点検項目                                   | 判定・備考                                                                                 |
| --- | ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| C-1 | 保有する情報資産を正確に把握し必要最小限化 | 「不要な情報は持たない」原則。窃取された場合の脅迫・不正売買等の二次被害拡大傾向を踏まえる |

### 共通: 情報収集の強化

| ID  | 点検項目                                                             | 判定・備考                                                     |
| --- | -------------------------------------------------------------------- | -------------------------------------------------------------- |
| D-1 | 公的機関・セキュリティベンダー公表の不審IP/ログ痕跡（IoC）を継続収集 | 当面の継続タスク。後出しされる調査情報を自組織のログ照合に利用 |

## 2. 速やかに取り組むべき継続対策

### 外部公開アプリケーション

| ID   | 対策項目                                                  |
| ---- | --------------------------------------------------------- |
| PA-1 | 外部公開範囲の見直し                                      |
| PA-2 | 認証機能（多要素認証・パスワード）の強化                  |
| PA-3 | アカウントへの権限付与の見直し                            |
| PA-4 | API連携等アプリケーション構成要素単位での管理状況の見直し |
| PA-5 | アプリケーション構成要素単位での権限付与等見直し          |
| PA-6 | ログ取得内容・保持期間の見直し                            |
| PA-7 | 追加実装可能なセキュリティ対策の検討                      |

### 利用外部サービス

| ID   | 対策項目                                                  |
| ---- | --------------------------------------------------------- |
| PS-1 | 認証機能（多要素認証・パスワード）の強化                  |
| PS-2 | アカウント付与の範囲見直し                                |
| PS-3 | アカウント棚卸の運用見直し                                |
| PS-4 | API連携等アプリケーション構成要素単位での管理状況の見直し |
| PS-5 | ログ取得内容・保持期間の見直し                            |
| PS-6 | 適用可能なセキュリティ対策の検討                          |

### 保有データ

| ID   | 対策項目                                       |
| ---- | ---------------------------------------------- |
| PD-1 | データ保有の是非の再検討                       |
| PD-2 | データ保管場所の再検討                         |
| PD-3 | データアクセスのログ取得内容・保持期間の見直し |
| PD-4 | データの暗号化                                 |

## 3. Kyberion への適用マッピング

| 項目                                     | 既存 capability / 実装先                                                                                                                                                |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-3 パッチ未適用                         | `pipelines/dependency-vuln-scan.json`（日次・ledger append 済）。構成要素は依存だけでなく基盤ソフトウェアまで拡張対象                                                   |
| B-1/B-2 網羅的洗い出し・ログ確認権限整理 | テナント外部サービス台帳（`knowledge/confidential/{tenant}/security/`、facade 管理）が記録先。棚卸し手順は `../../procedures/system/external-asset-inventory.md` に従う |
| A-2/B-2 ログ異常                         | `system:collect_logs` + `system:sre_analyze`、平時ベースラインとの差異検出。異常判定時はインシデント記録 → `incident-review` へ                                         |
| B-3 アカウント異常                       | `account-audit` 型パイプライン: サービス管理APIまたは `browser-actuator` で棚卸、想定外アカウント・無効化未反映を検出                                                   |
| C-1/PD-1..4 データ最小化・暗号化         | データ分類台帳 + storage-layout の tier 配置規則（`system/` vs `<tier>/`）との照合                                                                                      |
| D-1 IoC 収集                             | `advisory-watch` 型パイプライン: IPA/JVN/NCO/JPCERT 公表情報を `network:fetch` で定期取得し台帳サービスと照合                                                           |
| 判定後の対応                             | `pipelines/fragments/security-incident-containment.json`（証拠収集→`approval:request` ゲート→封じ込め→監査記録）。対応アクションは全て承認ゲート経由                    |
| 点検の定期実行                           | テナント `pipelines/*.json` の `schedule` + 人間の内容承認（project-trust）で chronos が自律実行                                                                        |
| 検査基準の深度                           | リモート検査可能項目は `../security/owasp_asvs.md` L1 相当を既定、機微情報取扱いは L2+                                                                                  |

## 4. 関連する政府・公的機関の参照先

- 経済産業省: サイバーセキュリティ経営ガイドライン（経営者リーダーシップ下での対策推進）
- IPA: 中小企業の情報セキュリティ対策ガイドライン第4.0版 / 「5分でできる！情報セキュリティ自社診断」
- IPA: SCS評価制度（サプライチェーンのセキュリティ対策評価、2027-03 制度開始予定 — 取引先・委託先を含む把握が将来要件化）
- 注意喚起の並行発信: NCO（国家サイバー統括室）、金融庁、警察庁、個人情報保護委員会、JPCERT/CC
