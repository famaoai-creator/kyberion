# A2B攻撃 早期検知のための Observability 調査レポート

**調査日:** 2026-10-31
**スコープ:** 公開アプリの解析を起点にバックエンド API を総当たりする攻撃(生成AIによる高度化を含む)を早期検知するためのシステム observability のあり方

---

## 0. エグゼクティブサマリー

2026年10月、NICT(情報通信研究機構)の脅威情報分析チーム LETTICE が、国内で相次ぐ情報漏えい事案の原因の一つとして「**A2B攻撃(App-to-Backend Attack)**」を特定・命名した。攻撃者は公開 Android アプリ(APK)を解析し、バックエンド API の接続先・仕様・認証方式を奪取した上で、サーバ側の認証・認可不備を狙い撃ちする。生成AIによってアプリ解析と脆弱性探索が効率化され、攻撃者の技術的障壁が下がっている。総務省も 2026-10-09 に注意喚起を発出している。

A2B攻撃の検知が難しい本質は、**攻撃リクエストが「構文的には完全に正規」である**点にある。アプリから抽出した正しいエンドポイント・正しいペイロード形式・正しい認証トークンで来るため、シグネチャ型WAFやパターンマッチはほぼ無力。有効なのは**セッション/プリンシパル単位の行動的・構造的シグナル**であり、それを可能にするのが本レポートで整理する observability 設計である。

要点:

1. **前提となる可視化**: APIインベントリ(shadow/zombie API 含む)とスキーマベースラインが無ければ「異常」の定義ができない。まず全APIを観測対象にすること。
2. **クライアント側の証拠は信用しない**: UA・TLSフィンガープリント・マウス軌跡は実ブラウザ/実端末由来のため真正に見える。**サーバサイドでしか観測できない構造的特徴**(呼び出しグラフ形状、リソース取得の完全性、負荷下でのタイミング相関)を主シグナルにする。
3. **単一イベントではなくセッション相関**: 一発のリクエストは合法に見えても、シーケンス・レート・スコープの総体として攻撃が浮かぶ。検知の最小単位はリクエストではなくセッション/プリンシパル/認証情報。
4. **段階的レスポンス**: 検知即ブロックではなく flag → challenge → throttle → block のグラデーション。誤検知コストと検知速度のバランスを取る。
5. **IoCよりTTP**: 攻撃元IPは使い捨て。行動パターン(列挙の網羅性、タイミング規則性、BOLA的ID走査)を検知ロジックの中核にする。

## 1. 脅威の整理:A2B攻撃とは何か

### 1.1 攻撃メカニズム(NICT LETTICE による特定)

| フェーズ | 攻撃者の行動                                                                                                                 | 防御側が見えるもの                                                         |
| -------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| ① 解析   | 公開APKを取得・逆コンパイル(JADX/apktool/IDA)。AI(LLMエージェント)でエンドポイント抽出・認証方式推定・脆弱性仮説生成を自動化 | **何も見えない**(オフライン作業)                                           |
| ② 偵察   | 抽出したエンドポイントへの試行。API仕様の再確認、認証フローの確認、応答のフィンガープリント                                  | 少数のプローブ、404/401/403の散発、仕様外パラメータ                        |
| ③ 攻撃   | 認証バイパス、IDOR/BOLAによるオブジェクト走査、SSRF、SQLi、RCE、認証情報の総当たり                                           | **正規形式の大量リクエスト**、オブジェクトIDの連続走査、異常な成功パターン |
| ④ 窃取   | データの系統的な取得・外部送信                                                                                               | レスポンス量の異常、正常UXを伴わないデータアクセス                         |

ポイント:**アプリ自体に脆弱性が無くても成立する**。攻撃面はバックエンドAPIであり、「公開していないつもりの内部仕様」がアプリ配布を通じて漏れている。iOSアプリ、Webフロントエンドでも同型の攻撃が可能。

### 1.2 同時期の関連観測

- **総務省(2026-10-09)**: 不正アクセスによる個人情報漏えい事案の相次ぎを受け注意喚起。「アプリ側の制御のみに依存せず、サーバ側で適切な認証・認可・入力値検証を実施することが重要」と明記。
- **NEC CyIOC(2026-10)**: LLM搭載の自律型ペネトレーションツール「Cairn」(複数LLMエージェントが Nuclei/ffuf/Impacket 等を並列駆動する状態空間探索エンジン)による日本企業を含む攻撃痕跡を確認。最頻出の成功手法は**未認証APIアクセス/認証バイパス**。
- **GreyNoise/Zenity(2025-12〜)**: LLM系エンドポイントへの大規模列挙キャンペーン。2 IP が11日間で 73+ エンドポイントへ 80,469 セッションを生成。無害に見えるフィンガープリント用プロンプトで応答モデルを特定する手法。
- **Imperva 等の業界観測**: コーディングエージェントが「トラフィックのパターンから未文書化エンドポイントを推論し、PoCエクスプロイトを生成し、数千の順列を人間より速く試す」段階に到達。正当な形式のリクエストを連鎖させて BOLA を行うため従来WAFを回避する。

### 1.3 なぜ従来の検知が効かないか

| 従来の防御                                  | A2B/生成AI攻撃に対して                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------ |
| シグネチャ型WAF                             | ペイロードはアプリ仕様どおりの正規形式。悪性パターンが無い               |
| IPレート制限                                | 分散プロキシ/居住IPローテーションで薄まる。低速化はAIが容易に適応        |
| UA/TLSフィンガープリント                    | uTLS・実ブラウザ制御(Playwright等)で真正なフィンガープリントが提示される |
| 行動バイオメトリクス(マウス/キーストローク) | LLM駆動ブラウザは人間分布内の入力を生成する                              |
| 静的API仕様ベースのアクセス制御             | 攻撃者は公開アプリから仕様を正確に入手済み                               |

**帰結**: クライアントが提示する証拠は全て偽装可能とみなし、**サーバサイドの構造的特徴量**で検知する設計が必要。

## 2. Observability 設計原則

### P1. 「見えないものは守れない」— APIインベントリが検知の前提

検知ルールは「何が正常か」を知って初めて機能する。A2B攻撃は文書化されていない/shadow API も狙うため:

- ゲートウェイ/LB/サービスメッシュの**実トラフィックから API カタログを自動生成**(endpoint × method × 認証要否 × 想定コンシューマ)。
- OpenAPI/GraphQLスキーマとの**ドリフト検出**: 実トラフィックに現れたが仕様に無いパス、仕様にあるが正常には呼ばれないパスを可視化。
- アプリが「正規に呼ぶはずのAPI集合」と「到達可能なAPI集合」の差分を攻撃面として管理。

### P2. 検知単位はリクエストではなくセッション/プリンシパル

A2B攻撃の個々のリクエストは正規品。**セッション(または認証プリンシパル)単位で以下を集約**することが検知のコア:

- 呼び出したエンドポイントの系列・網羅率・グラフ形状
- リクエスト間隔の分布(変動係数)
- 4xx/5xx の比率と遷移
- 静的リソース取得の有無(ブラウザ経由トラフィックの場合)
- 単位時間あたりの応答バイト数・レコード取得数

### P3. 構造シグナル > 表層シグナル

偽装コストの高い順にシグナルを信頼する。セッションの「形」(グラフトポロジ、タイミング相関、リソース取得パターン)は、攻撃の目的達成と両立しないため偽装が高コストか自己矛盾的。UA・Referer・TLS証拠は補助シグナルに留める。

### P4. 段階的レスポンスと短命な強制

複合スコアに応じて flag(監視のみ) → challenge(CAPTCHA/JSチャレンジ/PoW) → throttle → block と段階化し、統計的シグナル由来の強制には短いTTL(15-60分)を付ける。初期2週間は block 判定を人手レビューして精度を確かめてから自動強制に接続する。

### P5. 早期検知を「速さ」で設計する

「早急に検知」が要件である以上、検知レイテンシをKPIとして設計する:

- **ストリーミング処理**(Kafka/Kinesis + 数秒〜1分の recording rule)を標準とし、バッチ夜間集計はフォレンジック用途に留める。
- 第1段は**1リクエストで計算できるシグナル**(既知フィンガープリント、指定外ヘッダ、未文書化パス)でミリ秒判定、第2段は**セッション集約シグナル**で数十秒〜分判定、第3段は**履歴ベースライン比較**で時間単位判定、という多段構成。

## 3. 取るべきテレメトリ

「標準のcombinedログでは検知に必要なフィールドが欠けている」が最大の落とし穴。以下を構造化ログ(JSON)として確保する。

### 3.1 エッジ/L7プロキシ(nginx/Envoy/CDN)

```nginx
# 検知に必要な拡張フィールド(combined形式では欠落する)
log_format detection escape=json '{'
  '"ts":"$time_iso8601","ip":"$remote_addr","xff":"$http_x_forwarded_for",'
  '"method":"$request_method","uri":"$uri","args":"$args","status":"$status",'
  '"bytes_sent":"$bytes_sent","request_time":"$request_time",'
  '"upstream_response_time":"$upstream_response_time",'
  '"ua":"$http_user_agent","referer":"$http_referer",'
  '"ssl_protocol":"$ssl_protocol","ssl_cipher":"$ssl_cipher",'
  '"http2":"$http2","http2_stream_id":"$http2_stream_id",'
  '"session_id":"$cookie_session_id","request_id":"$request_id"'
'}';
```

必須フィールドの意味:

- `session_id` / `request_id`: セッション相関の生命線。クライアント制御のCookieに依存しすぎないよう、認証トークン由来のサーバサイドプリンシパルIDも別途記録。
- `upstream_response_time`: 「負荷下タイミング相関」シグナルに必須。
- `http2_stream_id` / `ssl_cipher`: push拒否(RST_STREAM)やTLS証拠の補助。
- **TLS終端点での JA4/JA4H フィンガープリント**(CDN/edgeで取得可能なら付与)。AIエージェントのフレームワーク署名の照合に使う。

### 3.2 APIゲートウェイ/アプリ層

- **全リクエストの監査イベント**(成功を含む。攻撃は成功レスポンスで進行する): プリンシパル(ユーザ/クライアント/クレデンシャルID)、呼び出しオペレーション、認可判定結果、拒否理由、対象オブジェクト識別子の種別(自分の/他人のリソース)。
- 認証イベント: ログイン試行・失敗・トークン発行・失効・**ローテーション済みクレデンシャルでの呼び出し**(決定的検知: 失効後トラフィックは即アラート)。
- WAF/レート制限/ガードレールイベントを個別メトリクスとして保持(`deny`理由をラベル化)。
- オブジェクトレベル認可(IDOR/BOLA検知用): 「プリンシパルがアクセスしたリソースのオーナー」をログ属性に含める。連続した他人リソースIDへのアクセスは最重要シグナル。

### 3.3 インフラ/ネットワーク

- **DNSログ**: ブラウザの pre-resolution(参照ページに無いホストの先行解決)有無。直接深いURLに飛ぶエージェントはpre-resolutionを生成しない。
- **WebSocketフレームタイミング**: 心拍間隔の変動係数。人間操作駆動は不規則、エージェントのイベントループ駆動は規則的。
- ** egress / SSRF監視**: サーバ発の外向き接続(メタデータエンドポイント、OASTコールバック)をDNS層で監視・遮断。

### 3.4 分散トレース(OpenTelemetry)

- セッションIDを baggage/attribute で伝播し、**セッションのAPI呼び出しグラフ**を再構成できるようにする。グラフ形状(直径・分岐率・パスエントロピ)が最有力シグナルの一つ。
- GraphQL/BFF ではオペレーション名・解決フィールドを span attribute に入れる(エンドポイント同一でも意味が違うため)。

## 4. 検知シグナル一覧(攻撃フェーズ別)

### 4.1 偵察・列挙フェーズ

| シグナル                   | 観測方法                                                     | A2B/AI攻撃での挙動                                                   |
| -------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------- |
| エンドポイント網羅率       | セッション/IPが触れたユニークエンドポイント数 ÷ カタログ総数 | API仕様を持っているため「仕様書順に総舐め」する。短期間で高網羅率    |
| パス列挙の系統性           | URI系列の編集距離・共通プレフィックス分析                    | `/v1/users/1`→`/2`→`/3` のようなID連番、または仕様ツリー順走査       |
| 4xxバースト                | `status=~4..` のセッション/ASN単位集計                       | 存在しないエンドポイントや権限外パスへの試行で404/403が集中          |
| 未知パス率                 | APIカタログ照合で未登録パスへのヒット率                      | 解析で得た古い/内部用パスの試行                                      |
| フィンガープリントプローブ | レスポンス内容を見るだけの無害な定型リクエスト               | 「hi」「モデル名を聞く」等の定型クエリ(GreyNoise観測と同型)          |
| プロトコル探索             | 仕様外のmethod・content-type・バージョンプレフィックス試行   | OpenAPI仕様書取得→試行、バージョンずらし(`/v1/`→`/v2/`→`/internal/`) |

### 4.2 エージェント固有の行動シグナル(AI模倣に強い構造シグナル)

| シグナル                        | 指標                                                                              | 人間                                                 | エージェント                                                  |
| ------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------- |
| **API呼び出しグラフの線形性**   | OTelスパン/ログからセッションの呼び出しDAGを構築。直径、分岐率、パスエントロピ    | 高分岐・往復・離脱あり(エントロピ高)                 | 目的エンドポイントへ収束する短いDAG。分岐率~1.1、エントロピ低 |
| **リソース取得の完全性**        | ページ毎に期待される静的リソース(CSS/JS/font/画像/ビーコン)の取得率。API:static比 | API:static ≈ 1:3〜1:6。30-80並列サブリクエスト       | APIのみ。static取得がほぼゼロで比が反転(3:1+)                 |
| **負荷下タイミング相関**        | セッション内リクエスト間隔の変動係数(CV)と `upstream_response_time` の相関        | サーバが遅いと人間の間隔も伸びる(正相関)。CV 0.8-2.5 | LLMの処理完了次第で間隔一定。CV 0.1-0.4、負荷と無相関         |
| **意味的一貫性**                | リクエスト系列の意図カテゴリ遷移(閲覧→比較→操作)                                  | 探索的・迂回あり                                     | 「価格→在庫」のような抽出直結の狭い系列                       |
| **DNS pre-resolution ギャップ** | 参照ページ内ホストの事前DNS解決の有無                                             | ブラウザが自動で先行解決                             | 直接URL指定でpre-resolution無し                               |
| **WebSocket心拍の規則性**       | フレーム間隔の変動係数                                                            | 活動量に連動し不規則                                 | イベントループの固定tick                                      |
| **HTTP/2 push の消費**          | pushしたリソースへのRST_STREAM率                                                  | 受け入れてキャッシュ                                 | 不要なので即RST_STREAM                                        |

単独では誤検知があるため **複合スコア化**が前提(§5)。特に「リソース取得完全性」は単体精度が最も高いが、フロントエンドリリースと連動した期待リソースマニフェストの自動更新が運用条件。

### 4.3 なりすまし・認証フェーズ

| シグナル                 | 内容                                                                                                                                          |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| JA4/JA4H と UA の不整合  | ブラウザを名乗るがTLSスタックが非ブラウザ(またはその逆)。エージェントフレームワークの既知署名照合                                             |
| ヘッダ一貫性             | Accept/Accept-Language/Accept-Encoding/Referer の欠落・非ブラウザ組合せ                                                                       |
| 送信元分類               | データセンターASN、匿名化(VPN/Proxy/Tor)、居住IP偽装。攻撃観測の多くは特定ASNに集中                                                           |
| アプリ証明の欠落         | Android向けAPIで Play Integrity / App Attest / 独自アテステーションが無い or 失敗している呼び出し(A2B攻撃はアプリ外クライアント)              |
| クレデンシャル異常       | 同一トークンの複数IP/地理同時使用、ローテーション後クレデンシャルのトラフィック(決定的)、プリンシパルの行動ベースラインからの複数特徴同時逸脱 |
| Credential stuffing 形状 | 認証エンドポイントへの低速分散試行 + 長セッションにアイドルギャップが無い                                                                     |

### 4.4 搾取・窃取フェーズ

| シグナル       | 内容                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------- |
| BOLA/IDOR 走査 | プリンシパルが「自分以外のオーナーのリソース」へ連続アクセス、オブジェクトIDの連番/規則的走査                       |
| スコープ濫用   | 許可された操作だが対象がベースライン外(同じツール/APIで触れたことのないスコープ)                                    |
| シーケンス濫用 | 個々は合法でも組合せが異常(例: `list`→`export`→外部URLへの`post`)                                                   |
| データ流出量   | プリンシパル/セッション単位の応答バイト・取得レコード数のベースライン逸脱。正常UX(画面表示)を伴わないデータアクセス |
| 成功率異常     | 一般人は権限外アクセスで高率で失敗する。認可境界への連続成功は攻撃側が仕様を知っている証拠                          |

## 5. 検知パイプラインのアーキテクチャ

```
[Edge/CDN]   TLS fingerprint(JA4) + L7構造化ログ ─┐
[WAF/API GW] 監査イベント・deny理由・認可属性 ────┼─→ [Stream/Loki+Kafka]
[App/OTel]   セッション相関トレース・認可イベント ─┘           │
                                                             ▼
                                            [セッション化・プリンシパル集約]
                                                             │
                          ┌──────────────────────────────────┼──────────────────────────┐
                          ▼                                  ▼                          ▼
                  [即時シグナル]                     [集約シグナル]               [ベースライン比較]
                  既知JA4/ヘッダ検査                グラフ線形性/リソース完全性     プリンシパル履歴・量
                  未知パス/IoC                      タイミングCV/DNSギャップ       スコープ逸脱
                          └──────────────────────────────────┼──────────────────────────┘
                                                             ▼
                                                  [複合スコア(重み付け)]
                                                   >0.35 flag / >0.55 challenge
                                                   >0.80 block (TTL 15-60min)
                                                             ▼
                                          [Alertmanager → 強制endpoint / SOCキュー]
                                          [人手レビュー → ラベル → 重み再較正]
```

### 5.1 実装例(主要3種)

**(a) Loki/Prometheus: 高API量・低静的リソースのセッション**

```yaml
# loki ruler — 10分窓でAPI>50且つstatic<5のセッションを検出
- record: session:api_requests_10m
  expr: sum by (session_id) (count_over_time({job="edge-access"} | json | uri =~ "^/api/.*" [10m]))
- record: session:static_requests_10m
  expr: sum by (session_id) (count_over_time({job="edge-access"} | json | uri =~ "^/static/.*" [10m]))

# Prometheus alert
- alert: HighApiLowStaticSession
  expr: session:api_requests_10m > 50 unless session:static_requests_10m > 5
  for: 5m
  labels: { severity: high, signal: resource_incompleteness }
```

**(b) 負荷下タイミング相関(エージェント判定で最も強い単独シグナルの一つ)**

```yaml
- record: session:inter_request_interval_cv:5m
  expr: stddev_over_time(session:inter_request_interval_p50:5m[5m]) / avg_over_time(session:inter_request_interval_p50:5m[5m])

- alert: AgenticTimingDecorrelation
  expr: session:inter_request_interval_cv:5m < 0.35 and avg_over_time(upstream_response_time_seconds[5m]) > 0.5
  for: 2m
  labels: { severity: high, signal: timing_decorrelation }
  # 「サーバが遅いのに間隔が一定」= 人間の応答待ちではない
```

**(c) 複合スコア(重み例。ラベル付き自社データで較正すること)**

| シグナル           | 重み例 | 根拠                                    |
| ------------------ | ------ | --------------------------------------- |
| リソース取得完全性 | 0.30   | 単体精度最高(偽装に5-10×のコストが必要) |
| タイミング規則性   | 0.25   | 負荷相関の消え方が構造的                |
| グラフ線形性       | 0.25   | 抽出目的のセッション形状を直接捕捉      |
| 意味的一貫性       | 0.15   | 補助(ルールベース分類で十分)            |
| push拒否等         | 0.05   | 補助(HTTP/2前提)                        |

`block > 0.80 / challenge 0.55-0.80 / flag 0.35-0.55`。自動化トラフィック比率5%の環境での block 段 precision 期待値は 0.85-0.92(全シグナル稼働時)。

### 5.2 欺瞞(deception)の活用

- **Honey endpoint**: カタログ外・正常フローから辿れないパスを仕込み、ヒット=確定的検知。アプリ解析で得た仕様に存在しないパスへの到達はほぼ攻撃。
- **Canary token/ID**: レスポンスに埋め込んだ追跡IDが外部(OAST/DNS)で観測されたら侵害確定。
- エージェント用に `robots.txt`/API規約で許可されているクローラ(GPTBot等)と、偽装エージェントを**分けて可視化**。AI系UAを一律ブロックすると正規連携を壊すため、class 分類(human / known_bot / ai_agent / malicious_automation)とポリシー別対応にする。

### 5.3 SIEM/SOC統合

- 各シグナルを個別メトリクス・個別アラートとして残し、複合スコアとは別に「どのシグナルが効いたか」をラベルで引き継ぐ(精度改善と誤検知分析に必須)。
- 相関の責務はSIEM側: 「依存関係侵害 → ツール呼び出し逸脱 → クレデンシャル濫用 → 流出」の多段相関は単体ツールでは繋がらない(ARMOの指摘どおり、CNAPP+SIEM+WAFの分断が最大の盲点)。
- Sigma等の detection-as-code で検知ルールを版管理し、攻撃TTPの変化に対してルールをリリース管理する。

## 7. 限界・トレードオフ

| 課題                         | 内容と対処                                                                                                                                                                                                                                                                  |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 誤検知                       | プライバシーツール(広告ブロッカー)はリソース完全性を壊す→CSS/font(ブロッカーは止めない)を必須項目化。不安定回線のモバイルはタイミングCVが下がる→RTT/ECTヒントで閾値を緩和。パワーユーザや正規B2B APIクライアントは線形グラフになる→認証履歴の長いプリンシパルは重みを下げる |
| 短時間バースト               | 10分窓の集計は<10分のスクレイプを取り逃がす→単発ページビュー時点でのリソース完全性チェックを併用                                                                                                                                                                            |
| リソースマニフェストの陳腐化 | フロントエンドリリースでCSSハッシュが変わると正規ユーザが不全判定される→ヘッドレスクロールによるマニフェスト自動生成をリリースパイプラインに組込み(自動化しないとシグナルは急速に劣化)                                                                                      |
| 適応する回避                 | 完全なリソース取得を真似る回避は可能だが攻撃コストを5-10倍にする。「完全性スコア0なのにAPIパターンが怪しい」非対称自体をシグナル化できる                                                                                                                                    |
| HTTP/1.1での欠落             | push/RST_STREAMシグナルはHTTP/2のみ。ブラウザUAなのにH2非対応自体を弱い副シグナルに転用                                                                                                                                                                                     |
| セッション相関の破断         | Cookie非保持/Torで相関が切れると正当利用がボット形状に見える→認証トークン由来のサーバサイドプリンシパルで相関する                                                                                                                                                           |
| プライバシー                 | セッション挙動の長期保持は監視強化と引き換え。ペイロードではなくメタデータで検知する設計(本レポートの方針)自体が最小化策になる。保持期間とアクセス権を明示                                                                                                                  |

## 8. 結論

A2B攻撃への observability の答えは「もっと多くのログ」ではなく「**検知に必要な形のテレメトリを、セッション/プリンシパル単位で相関できる形で**」である。優先度は:

1. **APIインベントリと実トラフィック差分の可視化**(何を守るかを確定)
2. **セッション相関できる構造化テレメトリ**(session_id・request_id・upstream時間・認可属性)
3. **構造シグナルの複合スコア**(列挙網羅率・グラフ線形性・リソース完全性・負荷下タイミング)
4. **段階的レスポンスと欺瞞**(honey endpoint、challenge、TTL付き強制)
5. **フィードバックループ**(誤検知ラベル→重み較正、検知ルールの版管理)

生成AIによる攻撃自動化は「攻撃者が正規仕様を持っている」ことを前提に防御側も設計を変える必要がある、という構造変化であり、検知は表層特徴から**行動構造とベースライン逸脱**へ軸足を移すのが本質的な対応となる。
