# Documentation Localization Policy

Kyberion supports localization, but the documentation system must retain a single canonical source of truth.

## Canonical Rule

Official architecture, governance, and contract documents should be authored in English first.
English is the canonical source unless a document explicitly states otherwise.

## Localization Rule

Localized documentation is allowed when it materially improves operator usability, onboarding, or communication quality.
However, localized variants should be treated as `derived operator aids`, not as the primary contract source.

## Recommended Structure

Use colocated language variants when a document has a localized counterpart:

```text
docs/
  <canonical-doc>.md
  <canonical-doc>.ja.md
```

For knowledge documents, prefer the same colocated pattern:

```text
knowledge/public/
  <document>.md
  <document>.ja.md
```

## What Should Usually Stay Canonical

These documents should usually remain English-first:

- architecture
- governance
- schemas
- system contracts
- operating policies
- actuator contracts

## What Is Good to Localize

These are good candidates for localization:

- operator instructions
- onboarding aids
- quick-reference guides
- UI labels
- status summaries
- clarification prompts

## Vocabulary Rule

UI- and operator-facing wording should not be localized by scattering translated strings across surfaces.
Instead, surfaces must go through the governed, namespaced catalog:

- [`knowledge/product/orchestration/user-facing-vocabulary.json`](../knowledge/product/orchestration/user-facing-vocabulary.json)

Keys live under `domains.<namespace>` (`cli`, `chronos`, `status`, `error`, `question`, `common`,
`bridge`, `concierge`, `onboarding`, …) rather than one flat list, so a key's owning surface is
visible from its qualified `namespace:key` form. `required_locales` on the catalog is the list of
locales every key must define — adding a locale is a data edit to that array plus
`pnpm generate:vocabulary-types`, never a hand-edited type union.

The single type-safe entry point is `t(key, params?, locale?)` (`libs/core/t.ts`). `key` is a
generated union (`libs/core/vocabulary-keys.generated.ts`), so referencing a key the catalog does
not define is a compile-time error, not a runtime "renders the key itself" surprise. `params`
render through an intentionally small ICU MessageFormat subset (`libs/core/message-format.ts`):
simple `{name}` interpolation and `{count, plural, one {...} other {...}}` — nothing more (no
gender/ordinal/date sub-formats; those stay in `libs/core/format.ts`'s locale/timeZone-aware
formatters, not in the catalog). A locale left untranslated for a given key falls back to
`default_locale` and logs one `[t]`-prefixed warning per call rather than failing silently or
rendering blank text.

This rule applies mainly to `fixed labels`, `section headers`, and short status words.
It does not require every free-form explanation or clarification sentence to be pre-translated.
Those may be generated by the LLM from canonical English-oriented contracts.

New hardcoded user-facing strings in `libs/core`, `scripts`, and the presence/satellite surfaces
are caught by a ratchet, not by hope: `pnpm check:i18n`
(`knowledge/product/governance/i18n-baseline.json`) freezes the current violation count per file
and fails only on an _increase_ — existing debt is allowed to shrink over time but never grow.
`pnpm check:catalogs` is the companion gate for the catalog itself (missing required-locale
entries, undefined/unused key references, placeholder mismatches across locales).
`pnpm report:i18n-coverage` is a related but distinct instrument: it reports per-locale,
per-namespace coverage percentages and the specific missing keys, which is what you read when
deciding whether a still-growing locale is ready to be promoted into `required_locales` — it is
informational and never fails a build, unlike the two gates above.

## Drift Rule

If a localized document diverges from the canonical English source, the English source wins.
Localized copies should be updated as soon as practical.

## Practical Guidance

Use English for:

- contracts
- schemas
- architecture
- governance

Use localization for:

- presentation
- conversation
- operator experience

This keeps the system globally understandable while still making local operation comfortable.
