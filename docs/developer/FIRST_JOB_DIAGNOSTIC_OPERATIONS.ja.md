# 最初のローカル診断を試す

プロフィール登録、実行設定、人間の承認は別の状態です。プロフィールの保存や baseline の all_clear は、仕事の実行権限を意味しません。

## 1. ホームから確認する

Presence Studio のホームにある「最初の仕事」から `/first-job` を開きます。初期状態では設定不足を表示します。画面を開く・更新するだけでは、テナント、依頼、承認、実行は作成されません。

この入口は固定の公開診断データ専用です。自由文、既存の機密情報、外部 AI、外部配信を扱いません。通常の Concierge へのフォールバックもありません。

### 準備状況と次の操作

診断設定がまだない場合も、同じ画面で設定状況を確認できます。各項目の「利用者」「設定担当者」は、次の操作を担当する人を示します。表示は案内であり、実行・承認の権限を与えるものではありません。

- 基本設定は、アクティブなプロフィールのファイルが存在するかだけを確認します。内容の正しさやオンボーディング完了は検証しません。権限不足などで読めない場合は「存在しない」とせず、確認できない状態を表示します。
- 診断の対応付け、ブラウザーのログイン設定、現在の本人確認、対象テナントでの承認範囲を分けて表示します。ログイン設定があっても IdP への接続成功は未確認です。
- 本人確認は、署名付きブラウザーセッションと現在の有効なメンバーへの外部 ID の紐づけを確認します。別の有効なアカウントでログインしても、依頼の所有者との一致や対象テナントの役割を満たさなければ承認できません。
- baseline は画面では実行せず、全体の正常性も保証しません。この定型診断には AI モデルは不要で、ほかの AI の仕事の準備状況は未確認です。
- 承認欄に何も表示されていない場合、明示的な tick が承認の表示や承認済みの依頼を進めるために必要なことがあります。保留の回復が必要な依頼や、結果が不確かな送信には tick を勧めません。終了済みの古い依頼は、別の承認を伴う新しい依頼の進行とは分けて扱います。

読み取りでは設定・資格情報・所属・権限を作成せず、外部プロバイダーの接続確認やログインも開始しません。通常のアクセス監査は従来どおり記録されます。個人の氏名、外部 ID、秘密情報、保護されたファイルの内容は、この準備状況の応答に含めません。

画面を離れた後は、戻った時点で状態を読み直します。送信結果が不明な場合は、古い準備完了表示を残さず、元の依頼を保持して確認を待ちます。更新や再表示だけで依頼・承認・回復操作を再送しません。

## 2. オペレーターが明示的に設定する

通常のオンボーディングとビルドを完了した環境で、新しい検証専用テナント名を選びます。進行中の mission や別テナントの実行コンテキストから設定しないでください。

```bash
pnpm onboarding first-job --tenant my-public-diagnostic --json
```

これは読み取り専用の計画です。内容と `plan_digest` を確認してから、表示されたダイジェストを指定します。

```bash
pnpm onboarding first-job --tenant my-public-diagnostic --apply --accept-plan <plan_digest> --json
```

作成対象は検証専用テナント、public の固定診断 charter、およびその1件に結び付く利用者・パイプラインの対応付けです。組織やプロジェクトは作りません。既存の無関係なテナントや変更済み設定を再利用せず、paused/retired の dot を自動再開しません。認証資格情報、人間のメンバー、承認記録は作成しません。

計画後に設定が変わると適用を拒否します。途中で失敗した場合は、残った設定を確認して計画を取り直してください。既存データを消してやり直す操作ではありません。

Presence の通常起動には別の owner メンバー初期化があります。owner が未作成の環境では、既存テナントへの owner membership が追加され得ます。画面を読むだけの起動と考えず、管理者がこのアクセス付与を事前に確認してください。first-job の設定コマンド自体はこの処理を行いません。

## 3. 実際の人間としてサインインする

loopback の localadmin 接続だけでは人間の承認を証明できません。既存の [OIDC ログイン設定](SURFACE_OIDC_LOGIN_OPERATIONS.ja.md) と、有効な Kyberion メンバーへの外部 ID の結び付けが必要です。そのメンバーは画面の利用者と一致し、対象テナントの owner または approver である必要があります。

認証設定がない場合、画面は不足を表示します。セットアップコマンドがサインインを代行したり、資格情報を生成したりすることはありません。認証設定には別途、正規の管理手順が必要です。

## 4. 依頼、承認、実行、確認

1. 画面の固定診断を依頼します。
2. オペレーターが `pnpm onboarding first-job --tenant my-public-diagnostic --tick` を実行します。承認待ちになるまでの取り込みも、この明示的な処理で進みます。
3. サインインした本人が画面で対象、効果、期限を確認し、その1件を承認または却下します。
4. オペレーターが同じ tick を実行します。承認は自動生成されず、期限・設定・メンバー・署名が再確認されます。
5. 画面を更新して結果を確認します。tick の成功表示だけでは成果の完成を意味しません。

画面では、検証済みのメタデータ（形式、ハッシュ、依頼・改訂の識別子等）と成果本文を確認し、版ごとの本文を比較できます。読み取りは認証された会話の正確な成果・版・ハッシュに限定され、ローカルのファイルパスは公開しません。

形式変更の依頼は親成果に結び付き、改めて個別承認を必要とします。再読み込みしても承認を再利用したり、新しい依頼を自動作成したりしません。

## tick の結果と次の担当

`--tick --json` は、従来の `dot_id`、`first_job_url`、`recovery`、`next_step` に加えて次を返します。事前条件を満たさない場合の拒否は従来どおりで、実行や自動修復を始めません。

- `status: supervisor_pass_completed` と `pass_completed: true` は、1回の housekeeping / intake / executor 処理が終わったことを示します。成果完成の判定ではありません。途中の例外や housekeeping エラーでは `supervisor_pass_failed` / `false` になります。
- CLI の終了コードは、処理中の例外や housekeeping エラーによる未完了・失敗時は 1、1回の処理が完了した場合は 0 です。承認待ち・保留は処理失敗ではないため、終了コードだけでなく `outcome` と `next_actor` / `next_action` を確認してください。
- `outcome` は現在の対応を優先した分類です。`artifact_verified` は既存の読み戻しで実際の成果バイト列とハッシュを確認できた状態だけです。executor の done 行だけでは完成にしません。
- `awaiting_approval` は対象の現在有効な承認カードが pending の状態です。カード未生成や承認済みだが止まっている状態は、本人の承認待ちと混同しません。
- `held`、`uncertain`、`failed`、`configuration_changed` はオペレーターによる確認が必要です。期限切れ `expired`、却下等の `refused`、対象処理のない `noop` も分けます。
- `next_actor` は `user` / `operator` / `none`、`next_action` は `review_approval` / `review_request` / `view_artifact` / `inspect_execution` / `inspect_configuration` / `none` です。これは案内であり、実行や承認の許可ではありません。
- `stages` は各段階の completed / failed / not_run、`counts` は処理件数、`outcomes` は分類別件数です。過去の終了済み依頼も件数に含みますが、未解決の問題や今回の実行失敗を優先し、それがなければ新しい終了結果を案内します。

過去の検証済み成果があっても、新しい保留依頼や今回の実行失敗を成功表示で隠しません。実行後に対応付けや設定が変わった場合も再確認します。応答には成果本文、物理パス、生の例外や失敗理由を含めません。読み戻しは読み取り専用で、tick の回数、実行範囲、承認手順を増やしません。

## 停止・期限切れ・復旧

期限切れ、署名失効、設定変更、不確かな実行状態では処理を保持します。保存済みの履歴から未実行と証明できる保留依頼だけは、本人が画面で内容を確認し、未実行のまま終了できます。元の承認と終了記録を保持し、終了をサーバーで確認できた後に、別の依頼と別の承認で再開します。実行済みの可能性や証拠不足がある場合は回復を提供せず、オペレーター確認が必要です。既存の監査や依頼を消す、承認を書き換える、一般処理へ切り替える操作で回避しないでください。

## 信頼境界

署名は、構成済みサーバーのブラウザーセッション署名鍵を用途分離して利用します。クライアントの「認証済み」という申告やチャットの文字列は承認証明になりません。サーバーの鍵・ファイルを自由に変更できる主体に対する独立した耐改ざん証明ではありません。

診断の本体はローカル限定ですが、本人確認の OIDC ログイン自体は構成済み IdP と通信します。ローカル診断と外部認証を混同しないでください。
