# Web の組織・プロジェクト管理

Concierge の「組織」ナビゲーション、または設定の管理リンクから /management を開く。
テナント → 組織 → プロジェクトの選択を URL に保持し、同じ範囲のミッション一覧へ移動できる。
選択は権限を増やす操作ではない。サーバーは毎回、認証された本人・所属・閲覧範囲を検証する。

## 今回扱う操作

- 既存の有効なテナントで、組織を作成し、名前・目的を編集する。
- 有効な組織の下にプロジェクトを作成し、名前・概要を編集する。
- 作成時の ID はサーバーで生成する。所属先、機密区分、稼働状態はフォームから変更しない。
- 対象は confidential 階層。テナント新設、メンバーやロールの付与、削除、移動、デプロイは提供しない。
- ミッションは既存の一覧・承認済み操作へ接続する。管理画面から承認を飛ばして開始しない。

目的の文章を変えると、その目的の承認状態だけが draft に戻る。保存前の確認画面で再承認が必要になることを示す。
同じ目的のまま名前だけを変更する場合、目的の承認状態を変えない。組織・プロジェクトの稼働状態も変えない。

## 認証と範囲

書き込みには資格情報に結び付いた有効な human メンバー、選択テナントの owner 所属、confidential の閲覧権限が必要。
localadmin の文字列だけ、localhost 接続、Origin の一致だけでは管理権限にならない。
テナント・組織・プロジェクトの資格情報上の制限を独立して適用し、所属情報はロック取得後にも読み直す。
組織の作成は組織範囲が all の場合、プロジェクトの作成はプロジェクト範囲が all の場合に限る。
Cookie による変更は同一 Origin を要求する。

画面が確認した actor と範囲から作る contextId を保存要求でも照合する。
別タブで別の本人へログインした場合、以前の確認内容を新しい本人の操作として送信しない。

## 保存の実装境界

- organization-management と project-management の型付き facade が正本。HTTP から任意の CLI、パス、ロールを渡さない。
- concierge_management_reader / concierge_management_writer は Concierge だけが引き受ける。
- リクエスト単位の AsyncLocalStorage capability は通常の default_allow、SUDO、persona より先に上限として適用する。
- 許可はファイル内容の読み書き、ディレクトリ作成、メタデータ参照を分け、論理パスと実体パスの両方で検証する。
- プロジェクトの共有レジストリも対象の一ファイルに限定する。環境変数の project ID を認可として利用しない。
- メタデータ更新は全ミッションやタスクセッションの再集計を行わず、既存の対象レコードと投影だけを更新する。
- 固定のサービスロックと監査処理は、任意のコールバックを受け取らない信頼済み mediator 内で実行する。データと再送記録は exact capability 内で保存する。

新しい管理 mediator は専用 package subpath からのみ import する。汎用 @agent/core barrel には追加せず、管理権限を引き受ける呼び出し元を明示する。

既存のミッション承認と保存された組織・プロジェクト範囲が一致しない場合は、同じ範囲で承認を取り直す。古い承認を広い範囲へ移し替えない。

## 競合・中断・再送

更新は読み込んだ version を要求し、読み込み後の変更を検出すると 409 として再読込を求める。
サービスロックは Web 同士をプロセス間で直列化する。既存 CLI 全体はこのロックを共有しないため、CLI と Web から同じ対象を同時に更新しない。
確認した保存要求は requestId を保持し、同じ要求の明示的な再送で二重作成しない。
変更要求を自動再送しない。作成後は返された ID を選択し、一覧を更新する。
監査完了に失敗してもデータが保存済みなら、その状態を auditPending として返す。同じ要求の再送は監査だけを再試行する。
画面の「操作記録を再試行」は同じ requestId を維持する。本人・選択範囲の変更やページの再読み込みで画面内の再送情報を破棄するため、それ以降の復旧は保存済み receipt と監査記録を確認する運用で行う。
receipt は二重実行を防ぐ証拠として retention catalog の review_required に登録し、自動削除しない。

通常の例外では、変更前の対象ファイルを復元する。複数ファイルの保存と再送記録はプロセス終了に対して単一トランザクションではない。
保存途中でプロセスが落ちた場合、決定的な作成 ID の競合として停止することがある。別の requestId で無条件に再作成せず、監査・対象レコードを確認し、既存の管理 facade で復旧する。

## 回帰確認

resource-access-scope、organization-management、surface-management-mutations、管理 HTTP の本人/範囲テスト、management-ui を実行する。
さらに typecheck、core と両 Web アプリの build、完全な check、role-assumption reachability と authority role index、語彙型と疑似ロケールの鮮度を確認する。
重点は別テナント、狭い組織/プロジェクト制限、Cookie 本人変更、待機中の期限切れ、二重クリック、保存途中の失敗、監査の対象範囲である。
