# 情報資産のスコープモデル（管理・開示・加工）の設計

基準は `858cfafe2`（2026-11-05 の `origin/main`）。2026-11-05 の open PR レビュー
（#1407・#1411〜#1414）で見つかった不整合を、個別の修正ではなく概念の欠落として
整理し直すための設計である。

## 結論

情報資産に対する統制を、次の **3 つのスコープ**と **4 つの操作**に分けて表す。

| 区分     | 名前                   | 問い                                                   |
| -------- | ---------------------- | ------------------------------------------------------ |
| スコープ | 管理                   | この資産は誰の管理下にあるか                           |
| スコープ | 開示                   | 誰に、どこまで見せてよいか                             |
| スコープ | 加工                   | この資産から何を派生させてよく、派生物は何を引き継ぐか |
| 操作     | 作成・編集・削除・実行 | 誰がそれをしてよいか（既存の権限レイヤーで判定）       |

**tier（`personal` / `confidential` / `public`）は「開示と加工の上限を決める分類ラベル」に
役割を絞る**。いまの tier は「誰の資産か」と「どれだけ機密か」の二つを一つの値で表して
おり、これが外部送信の判定や退会時の削除の不整合の根になっている。

新しい汎用ストアは作らない。既存の `tenant_slug` / `scope_kind` / 保存区画 / tier /
viewer scope / provenance taint / Charter `information_flow` の上に意味づけを重ね、
判定関数を揃える。

## モデル

### 管理スコープ（custody）

資産の管理者を表す。値は 3 種類。

| 種類     | 管理者                                 | 物理表現（既存）                                             | 主な資産の例                               |
| -------- | -------------------------------------- | ------------------------------------------------------------ | ------------------------------------------ |
| `system` | インストールの運用者                   | `system/` 区画、`scope_kind: system`                         | システム全体のロール、製品の設定、全体監査 |
| `tenant` | テナント（→組織→プロジェクト→…で細分） | `confidential/<tenant>/`、`knowledge/confidential/<tenant>/` | 顧客資料、テナントのミッション、委譲結果   |
| `person` | 個人（principal）                      | `personal/`、`knowledge/personal/`                           | 個人の調べもの、個人メモ                   |

管理者は次を決める主体である。

- 保存先（区画）と保持期間
- 退会・削除のときに何を消すか
- 開示・加工の許可（外部の処理者への証明を含む）を誰が出すか

`shared` / `public` は開示の結果であって管理者ではない。公開された製品知識の管理者は
`system` である。

### 開示スコープ（disclosure）

資産を見せてよい相手。内側から順に広がる。

| 段階 | 相手                         | 判定（既存）                                             |
| ---- | ---------------------------- | -------------------------------------------------------- |
| D1   | 管理者の内側                 | 包含チェーン、Viewer Scope                               |
| D2   | 特定の閲覧者                 | Viewer Scope（organization / project / tier の絞り込み） |
| D3   | 他の管理者（他テナントなど） | 仲介アクセス（deny-unless-brokered、監査必須）           |
| D4   | 外部の処理者（AI など）      | 推論送信・委譲の egress 判定、処理者の証明               |
| D5   | 外部の受領者（顧客・宛先）   | Charter の recipient、外部操作の承認                     |
| D6   | 公開                         | `public` tier、公開ナレッジへの昇格                      |

D4 と D5 は Charter と同じく区別する。処理者に見せることは受領者に渡すことではない。

### 加工スコープ（processing）

資産から派生物を作ること、およびその条件。

| 加工の種類       | 例                                                        |
| ---------------- | --------------------------------------------------------- |
| 変換・要約       | 要約、翻訳、レンダリング                                  |
| 蒸留・学習候補化 | ナレッジへの蒸留、memory 候補、HINTS                      |
| 索引化           | 埋め込み、検索インデックス、キャッシュ                    |
| 集計             | 複数の管理者にまたがる件数・ダッシュボード                |
| 処理者側での利用 | 外部の処理者による学習・保持（`training_use`、retention） |

`training_use` は開示ではなく加工の条件である。「処理者に見せる（D4）」と「処理者が
学習・保持しない（加工の条件）」の組み合わせが、外部の AI への送信になる。

### 操作（権限）

| 操作 | 管理スコープとの関係                            | 既存の仕組み                                               |
| ---- | ----------------------------------------------- | ---------------------------------------------------------- |
| 作成 | 生まれた時点で管理者が決まる。後から推測しない  | 作成時の `context` 設定、保存先の配置規則、governed writer |
| 編集 | 管理者の範囲内で、権限を持つ者だけ              | Authority Role、claim、書き込み範囲                        |
| 削除 | 管理者の保持方針に従い、派生物も一緒に消す      | 保持期間カタログ、offboarding、GC                          |
| 実行 | 資産を使って外部に作用する。開示（D4/D5）を伴う | 承認、Scope Envelope、grant、Charter                       |

### tier の役割

tier は**分類ラベル**とし、開示と加工の上限を決める。

| tier           | 既定の開示上限 | 既定の加工制限                                            |
| -------------- | -------------- | --------------------------------------------------------- |
| `public`       | D6             | 制限なし                                                  |
| `confidential` | D2             | D3 以上・処理者の学習は管理者の許可が必要                 |
| `personal`     | D1             | D3 以上・処理者の学習は管理者の許可が必要。集計に入れない |

tier は管理者を決めない。`personal` の資産の管理者は通常 `person` だが、その対応は
保存区画から導くものであって tier の名前から推測するものではない。

## 規則

| ID   | 規則                                                                                                                                               |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-01 | すべての資産は作成時に管理者（`system` / `tenant` / `person`）を持つ。管理者の無い既存の記録は `unscoped-legacy` として分け、推測しない。          |
| R-02 | 管理者の無い区画に、テナントや個人の資産を置かない（`system/` にテナントのデータを置かない、を一般化したもの）。                                   |
| R-03 | 開示の判定は、資産の管理者と分類ラベルと開示先から決まる。呼び出し元の申告（tenant / tier パラメータ）は範囲を狭めるだけで、広げない。             |
| R-04 | 外部の処理者への開示（D4）と加工の条件（`training_use` など）の許可は、資産の管理者が出す。`system` / `tenant` / `person` のどれも同じ形で出せる。 |
| R-05 | 同じ開示の問いに対して、入口（推論送信・委譲・閲覧）ごとに結論が変わってはならない。判定関数を共有する。                                           |
| R-06 | 派生物は元の資産の管理者を引き継ぐ。開示と加工の上限は、元の資産のうち最も厳しいものに揃える。                                                     |
| R-07 | 開示や加工の上限を広げるのは、承認つきの明示操作（`requestDeclassify`、公開ナレッジへの昇格）だけである。                                          |
| R-08 | 複数の管理者にまたがる派生物（集計など）は、仲介アクセスを経て、開示の上限を全員の共通部分に絞る。どれか一つの管理者に黙って帰属させない。         |
| R-09 | 削除は管理者の保持方針に従い、派生関係をたどって派生物まで及ぶ。保存先の手書きリストに頼らない。                                                   |
| R-10 | 編集・実行の権限は既存の権限レイヤーで判定する。開示の許可を編集・実行の許可に転用しない。                                                         |

## 既存概念との対応

| 既存の概念                                                  | 位置づけ                                             |
| ----------------------------------------------------------- | ---------------------------------------------------- |
| 包含チェーン、`tenant_slug`、`scope_kind: system`、保存区画 | 管理スコープ                                         |
| Viewer Scope、`includeUntenanted`                           | 開示スコープ（D1〜D2）                               |
| 仲介アクセス（brokered read）                               | 開示スコープ（D3）                                   |
| 推論送信・委譲の egress 判定、`provider-egress-policy.json` | 開示スコープ（D4）                                   |
| Charter `information_flow` の processor / recipient         | 開示スコープ（D4 / D5）と加工の目的                  |
| `training_use`、zero_retention、プロバイダの証明            | 加工スコープ（処理者側での利用の条件）               |
| provenance taint、`combineProvenanceTaint`                  | 加工スコープの R-06（mission 単位の実装）            |
| `requestDeclassify`、memory-promote                         | 加工スコープの R-07                                  |
| ingest asset ledger、memory provenance、resource provenance | 加工スコープの派生関係（分散している）               |
| 保持期間カタログ、scope-offboarding、GC                     | 削除操作                                             |
| Authority Role、claim、Scope Envelope、各種 grant           | 編集・実行操作                                       |
| tier                                                        | 開示・加工の上限を決める分類ラベル                   |
| Stance（`customer/{slug}/`）                                | 対象外。実行時の立場の設定で、資産のスコープではない |

GLOSSARY の「Scope terms」に並ぶ 5 つの意味（包含チェーン、Scope Envelope、Viewer Scope、
Work Visibility Scope、Binding Scope）はそのまま残る。このモデルはそれらを置き換えず、
「情報資産に何をしてよいか」を問うときの共通の枠組みとして上に重ねる。

**P3 の実施（MSN-SCOPE-P3-20261107）。**

- `libs/core/asset-derivation.ts` に派生関係を実装した。参照形式は一つ:
  `asset:{tenant}:{id}@v{n}`（ingest 台帳の資産）と `path:{repo-relative}`
  （任意の資産パス）。memory provenance の記録は `memoryProvenanceRefs`
  で `path:` 参照に写像してつなぐ（内容ハッシュ・`external:` の origin
  連鎖は provenance ストア側に残る — 実体のないパスは名乗らない）。
- 資産単位の taint（`AssetTaint` = highestTier・tenants・prohibitExternal）は
  参照解決で導出する — caller が taint を名乗れない（asset → 台帳の
  target_path、path → アンカーされた区画レイアウトで tier/custody を分類）。
  派生の taint は全源泉の最も厳しい合成（R-06）。`assertAssetShareAllowed`
  は mission 単位 `assertProvenanceShareAllowed` の資産版。
- 信頼モデル: 台帳は削除権限の信頼基点なので、内容は常に敵対的に扱う。
  - custody は**アンカーされた区画レイアウト**（knowledge/・テナントツリー・
    floor・登録済み runtime 区画 — 大文字小文字を畳み `tenantOfPath` 優先）で
    推定する。部分文字列の `confidential/{slug}` は管理者にならない
    （`tmp/job/confidential/acme/` は acme の区画ではない = custody
    laundering 防止）。
  - 記録パスは**派生可能なデータ区画**に限る（knowledge/・テナントツリー・
    floor — コード・設定・`.git`・runtime state・台帳自身は不可）。
    `recordDerivation`・削除・退会収集の 3 層で同じ天井を replay する。
  - replay は**区画束縛 honoring**（`recordedLandingHonored`）で行う。
    台帳行が名乗る custody は信用しない — `path:` ソースはアンカー
    レイアウトから、`asset:` ソースは ingest 台帳の実在確認から custody
    と taint を**再検証**し（`verifiedRecordSources`）、レコードは
    「自分が置かれた区画の管理者 ∈ 検証済みソース管理集合」のときだけ
    有効とみなす（`recordDerivation` が書く場所と同じ規則）。着地点は
    その区画の管理者か system に限られ、tier は検証済みソースから
    再計算した taint の床を超える必要がある — 他テナント・他 person の
    custody を名乗る偽造行は、自分の区画の到達範囲を一歩も越えられない。
    区画列挙自体もアンカー済み（`system/`・`confidential/{slug|common}`・
    `personal/{member}` のみ — 不正な区画名・読めない区画は警告つきで
    skip）。
  - 台帳区画は `tenant_scope.protected_prefixes` と
    `TIER_PARTITIONED_RUNTIME_ROOTS` に登録済み — 他テナント区画への
    書き込みは tenant binding が閉じ、台帳の tier 分類も正しい。
    `personal/{member}` はメンバー区画なのでテナント列挙からは除外する
    （`tenantTiers` carve-out — slug==member-id のテナント退会が
    メンバーの台帳を掃かない）。残余: system 区画の台帳は ambient
    persona 権限で書けるため、system 区画内の偽造は public/非管理
    データの削除に留まる — 専用 storeRole 化を強化案として後続に残す。
- `recordDerivation` は派生物が最も厳しい源泉より低い tier の区画に置かれる
  記録を refuse する（`[DERIVATION_TIER_VIOLATION]`、fail-closed）。
  ソースは実在し（path 参照）、asset 参照は ingest 台帳の target_path が
  参照テナントの木内かつ**派生可能なデータ区画**であることまで確かめる
  （偽造 ingest 行が `libs/` などを差しても届かない）。
- 派生台帳は**ソースの管理者区画**に append-only で置く
  （`active/shared/runtime/asset-derivations/{confidential/{T}|system|personal/{ref}}/`
  — 登録済み partitioned ledger root。複数管理者にまたがる源泉は各管理者の
  台帳に全ソース列を書く — どの区画が残っても閉包が完結する）。
- 削除は `deleteAssetWithDerivations` が台帳の遷移閉包（BFS・dedupe・サイクル
  安全）をたどり、葉から順に消す。閉包のシードは `path:{normalized}` の
  `derived.path` のみ（`derived.ref` は `path:` 形と不一致なら行ごと形状
  不正として捨てる）— そして**死亡伝播も区画束縛 honoring を通るレコード
  に限る**: 偽造行が「被害者のソースが死んだ」と標しても、その区画の
  honoring を通らなければ deadRefs に乗らず、被害者自身の正当レコードを
  使った削除ランダリングは起きない。**削除前に全候補を再検証**し、通常
  ファイルだけを消す — malformed / 形状不正 / 権利外の行は警告付きで
  skip し、監査は `derivation-deletions.jsonl` に deleted+skipped 両方で
  残る（削除失敗・消失候補も skipped に記録）。
- 退会: `collectScopeTargets` がテナントの派生台帳を読み（
  `scope-offboarding-derived.ts`）、収集済みツリーの外にある派生物を
  `derived_asset` 対象として拾う — 同じ区画束縛 replay を経るので、
  他 custody に落ちる行を名乗る偽造は export への持ち出し自体を防ぐ。
  対象は **runtime 区画ターゲットより前に** 並べ、台帳を名乗る区画が
  派生物より先に消えないようにする。`verifyScopeOffboarded` は収集済み
  対象 − soft-deleted の残存も直接数える（台帳が先に消えても失敗した
  削除が見えなくならない）。保持期間側への接続口は
  `listDerivedPathsForCustodian` / `listDerivedRecordsForCustodian`
  （janitor 配線は後続段階）。
- 受入 fixture テスト `libs/core/asset-derivation.test.ts`（19件）+
  `scope-offboarding.test.ts`（退会収集・外部着地点拒否）:
  資産→要約→蒸留（多段）・キャッシュ・委譲結果を記録し、資産削除で
  全て消えることを確認。加えて低 tier 区画への記録拒否・malformed
  ref/ソース・偽造 ingest 行（非派生区画の target_path）・custody
  laundering・両スペリング閉包・サイクル・改竄行（他テナント・非派生
  区画・形状不正・**検証済み foreign custody を名乗る偽造行** — 区画束縛
  で拒否、退会収集でも export しない・**被害者のソースを「死んだ」と
  標す偽造行による削除ランダリング** — deadRefs に乗らず被害者の
  グラフは無事）の削除防御を網羅。
- mission 単位の `provenance-taint.ts` は変えない — 資産単位は別の参照型として併置。

ファイル I/O の門番（tier-guard）でこのモデルを使う土台は、[保存先カタログと許可証による権限判定](./STORE_CATALOG_GRANT_GUARD_DESIGN_2026-11-05.ja.md)（G0〜G4）で先に整える。

## 非目標

- 新しい汎用の資産ストアや権限ストアを作らない。
- 保存区画のディレクトリ名（`personal/`、`confidential/`、`public/`）を変えない。
- 権限レイヤー（Authority Role、claim、Scope Envelope）を作り直さない。
- Stance（`customer/{slug}/`）をスコープに組み込まない。
- `provider-egress-policy.json` にインストール固有の契約内容を書かない（公開ファイルのため）。

### person の証明の規則（D-02）

- 承認できるのは本人だけ。承認依頼に本人（`accountability.consent.subject`）を記録し、`--principal <id>` の人の依頼を他の人（所有者を含む）が承認すると、承認の時点で拒否する（`what — why | next | evidence` 形式）。適用時と読み込み時にも、記録された承認者が本人かを確かめる。
- 本人が自分で開いた依頼を本人が承認するのは同意であって自己承認ではない。separation of duties の例外は `custody-provider-attestation` の承認領域で、承認者が記録された本人と一致するときだけに限る。system と tenant の証明の separation of duties は変えない。
- person の material を外部に送るには、本人の有効な同意と、学習に使わない証拠（有効な system の証明で `training_use: none`、または policy の宣言）の両方が要る。`approved_providers` の例外だけでは足りない（D-01）。
- 単一利用者のインストール（`--principal` なし、保存名 `operator`）では所有者が本人なので、所有者が system の証明と自分の同意を記録すれば足り、separation of duties で行き詰まらない。依頼には本人として所有者（`user:owner`）を記録する。
- 承認つき・監査つき・TTL の扱いは従来どおり。
- 移行: 本人以外が承認した既存の person の証明（たとえば変更前に所有者が承認したもの）は削除しない。読み込み時に「同意ではない」として扱い、拒否理由で本人の承認による記録し直しを案内する。

残る論点: policy の `training_use: none` 宣言があるとき、person の material は本人の同意なしでも送れる（従来どおり）。宣言は運用者が policy を編集したときだけ存在する。宣言があっても本人の同意を必須にするかは、次の判断とする。
