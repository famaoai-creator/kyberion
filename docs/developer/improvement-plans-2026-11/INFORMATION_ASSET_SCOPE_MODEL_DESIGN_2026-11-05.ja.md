# 情報資産のスコープモデル（管理・開示・加工）の設計

基準は `858cfafe2`（2026-11-05 の `origin/main`）。2026-11-05 の open PR レビュー
（#1407・#1411〜#1414）で見つかった不整合を、個別の修正ではなく概念の欠落として
整理し直すための設計である。

## 結論

情報資産に対する統制を、次の **3 つのスコープ**と **4 つの操作**に分けて表す。

| 区分     | 名前                   | 問い                                                   |
| -------- | ---------------------- | ------------------------------------------------------ |
| スコープ | 管理                   | この資産は誰の管理下にあるか                           |
| スコープ | 開示                   | 誰に、どこまで見せてよいか                             |
| スコープ | 加工                   | この資産から何を派生させてよく、派生物は何を引き継ぐか |
| 操作     | 作成・編集・削除・実行 | 誰がそれをしてよいか（既存の権限レイヤーで判定）       |

**tier（`personal` / `confidential` / `public`）は「開示と加工の上限を決める分類ラベル」に
役割を絞る**。いまの tier は「誰の資産か」と「どれだけ機密か」の二つを一つの値で表して
おり、これが外部送信の判定や退会時の削除の不整合の根になっている。

新しい汎用ストアは作らない。既存の `tenant_slug` / `scope_kind` / 保存区画 / tier /
viewer scope / provenance taint / Charter `information_flow` の上に意味づけを重ね、
判定関数を揃える。

## モデル

### 管理スコープ（custody）

資産の管理者を表す。値は 3 種類。

| 種類     | 管理者                                 | 物理表現（既存）                                             | 主な資産の例                               |
| -------- | -------------------------------------- | ------------------------------------------------------------ | ------------------------------------------ |
| `system` | インストールの運用者                   | `system/` 区画、`scope_kind: system`                         | システム全体のロール、製品の設定、全体監査 |
| `tenant` | テナント（→組織→プロジェクト→…で細分） | `confidential/<tenant>/`、`knowledge/confidential/<tenant>/` | 顧客資料、テナントのミッション、委譲結果   |
| `person` | 個人（principal）                      | `personal/`、`knowledge/personal/`                           | 個人の調べもの、個人メモ                   |

管理者は次を決める主体である。

- 保存先（区画）と保持期間
- 退会・削除のときに何を消すか
- 開示・加工の許可（外部の処理者への証明を含む）を誰が出すか

`shared` / `public` は開示の結果であって管理者ではない。公開された製品知識の管理者は
`system` である。

### 開示スコープ（disclosure）

資産を見せてよい相手。内側から順に広がる。

| 段階 | 相手                         | 判定（既存）                                             |
| ---- | ---------------------------- | -------------------------------------------------------- |
| D1   | 管理者の内側                 | 包含チェーン、Viewer Scope                               |
| D2   | 特定の閲覧者                 | Viewer Scope（organization / project / tier の絞り込み） |
| D3   | 他の管理者（他テナントなど） | 仲介アクセス（deny-unless-brokered、監査必須）           |
| D4   | 外部の処理者（AI など）      | 推論送信・委譲の egress 判定、処理者の証明               |
| D5   | 外部の受領者（顧客・宛先）   | Charter の recipient、外部操作の承認                     |
| D6   | 公開                         | `public` tier、公開ナレッジへの昇格                      |

D4 と D5 は Charter と同じく区別する。処理者に見せることは受領者に渡すことではない。

### 加工スコープ（processing）

資産から派生物を作ること、およびその条件。

| 加工の種類       | 例                                                        |
| ---------------- | --------------------------------------------------------- |
| 変換・要約       | 要約、翻訳、レンダリング                                  |
| 蒸留・学習候補化 | ナレッジへの蒸留、memory 候補、HINTS                      |
| 索引化           | 埋め込み、検索インデックス、キャッシュ                    |
| 集計             | 複数の管理者にまたがる件数・ダッシュボード                |
| 処理者側での利用 | 外部の処理者による学習・保持（`training_use`、retention） |

`training_use` は開示ではなく加工の条件である。「処理者に見せる（D4）」と「処理者が
学習・保持しない（加工の条件）」の組み合わせが、外部の AI への送信になる。

### 操作（権限）

| 操作 | 管理スコープとの関係                            | 既存の仕組み                                               |
| ---- | ----------------------------------------------- | ---------------------------------------------------------- |
| 作成 | 生まれた時点で管理者が決まる。後から推測しない  | 作成時の `context` 設定、保存先の配置規則、governed writer |
| 編集 | 管理者の範囲内で、権限を持つ者だけ              | Authority Role、claim、書き込み範囲                        |
| 削除 | 管理者の保持方針に従い、派生物も一緒に消す      | 保持期間カタログ、offboarding、GC                          |
| 実行 | 資産を使って外部に作用する。開示（D4/D5）を伴う | 承認、Scope Envelope、grant、Charter                       |

### tier の役割

tier は**分類ラベル**とし、開示と加工の上限を決める。

| tier           | 既定の開示上限 | 既定の加工制限                                            |
| -------------- | -------------- | --------------------------------------------------------- |
| `public`       | D6             | 制限なし                                                  |
| `confidential` | D2             | D3 以上・処理者の学習は管理者の許可が必要                 |
| `personal`     | D1             | D3 以上・処理者の学習は管理者の許可が必要。集計に入れない |

tier は管理者を決めない。`personal` の資産の管理者は通常 `person` だが、その対応は
保存区画から導くものであって tier の名前から推測するものではない。

## 規則

| ID   | 規則                                                                                                                                               |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-01 | すべての資産は作成時に管理者（`system` / `tenant` / `person`）を持つ。管理者の無い既存の記録は `unscoped-legacy` として分け、推測しない。          |
| R-02 | 管理者の無い区画に、テナントや個人の資産を置かない（`system/` にテナントのデータを置かない、を一般化したもの）。                                   |
| R-03 | 開示の判定は、資産の管理者と分類ラベルと開示先から決まる。呼び出し元の申告（tenant / tier パラメータ）は範囲を狭めるだけで、広げない。             |
| R-04 | 外部の処理者への開示（D4）と加工の条件（`training_use` など）の許可は、資産の管理者が出す。`system` / `tenant` / `person` のどれも同じ形で出せる。 |
| R-05 | 同じ開示の問いに対して、入口（推論送信・委譲・閲覧）ごとに結論が変わってはならない。判定関数を共有する。                                           |
| R-06 | 派生物は元の資産の管理者を引き継ぐ。開示と加工の上限は、元の資産のうち最も厳しいものに揃える。                                                     |
| R-07 | 開示や加工の上限を広げるのは、承認つきの明示操作（`requestDeclassify`、公開ナレッジへの昇格）だけである。                                          |
| R-08 | 複数の管理者にまたがる派生物（集計など）は、仲介アクセスを経て、開示の上限を全員の共通部分に絞る。どれか一つの管理者に黙って帰属させない。         |
| R-09 | 削除は管理者の保持方針に従い、派生関係をたどって派生物まで及ぶ。保存先の手書きリストに頼らない。                                                   |
| R-10 | 編集・実行の権限は既存の権限レイヤーで判定する。開示の許可を編集・実行の許可に転用しない。                                                         |

## 既存概念との対応

| 既存の概念                                                  | 位置づけ                                             |
| ----------------------------------------------------------- | ---------------------------------------------------- |
| 包含チェーン、`tenant_slug`、`scope_kind: system`、保存区画 | 管理スコープ                                         |
| Viewer Scope、`includeUntenanted`                           | 開示スコープ（D1〜D2）                               |
| 仲介アクセス（brokered read）                               | 開示スコープ（D3）                                   |
| 推論送信・委譲の egress 判定、`provider-egress-policy.json` | 開示スコープ（D4）                                   |
| Charter `information_flow` の processor / recipient         | 開示スコープ（D4 / D5）と加工の目的                  |
| `training_use`、zero_retention、プロバイダの証明            | 加工スコープ（処理者側での利用の条件）               |
| provenance taint、`combineProvenanceTaint`                  | 加工スコープの R-06（mission 単位の実装）            |
| `requestDeclassify`、memory-promote                         | 加工スコープの R-07                                  |
| ingest asset ledger、memory provenance、resource provenance | 加工スコープの派生関係（分散している）               |
| 保持期間カタログ、scope-offboarding、GC                     | 削除操作                                             |
| Authority Role、claim、Scope Envelope、各種 grant           | 編集・実行操作                                       |
| tier                                                        | 開示・加工の上限を決める分類ラベル                   |
| Stance（`customer/{slug}/`）                                | 対象外。実行時の立場の設定で、資産のスコープではない |

GLOSSARY の「Scope terms」に並ぶ 5 つの意味（包含チェーン、Scope Envelope、Viewer Scope、
Work Visibility Scope、Binding Scope）はそのまま残る。このモデルはそれらを置き換えず、
「情報資産に何をしてよいか」を問うときの共通の枠組みとして上に重ねる。

## 非目標

- 新しい汎用の資産ストアや権限ストアを作らない。
- 保存区画のディレクトリ名（`personal/`、`confidential/`、`public/`）を変えない。
- 権限レイヤー（Authority Role、claim、Scope Envelope）を作り直さない。
- Stance（`customer/{slug}/`）をスコープに組み込まない。
- `provider-egress-policy.json` にインストール固有の契約内容を書かない（公開ファイルのため）。
