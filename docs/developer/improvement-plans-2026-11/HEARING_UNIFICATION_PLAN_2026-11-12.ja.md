# ヒアリングを 1 つの概念にまとめる計画 (HR-01〜05)

- 概念の正本: [hearing-model](../../../knowledge/product/architecture/hearing-model.md)（concept-registry の `hearing`）
- 前提: [顧客との調整事項ヒアリングと決定の計画 (CD-01〜13)](../improvement-plans-2026-10/CUSTOMER_DECISION_HEARING_PLAN_2026-10-24.ja.md)

## 背景

Kyberion には「ヒアリング」と呼ばれる仕組みが複数あり、それぞれが別のデータ型と保存先を持っている。

| 仕組み                                                           | 答える人     | ゴールの定義                 | 回答の行き先                             | 次の作業                     | 集計               |
| ---------------------------------------------------------------- | ------------ | ---------------------------- | ---------------------------------------- | ---------------------------- | ------------------ |
| 顧客の決定ヒアリング（`customer-decision`、customer-room）       | 社外の顧客   | 製品のテンプレート 2 種だけ  | 決定台帳・決定記録                       | 種類ごとに決まった振り分け   | 覆された率など一部 |
| Front Desk のヒアリングシート（`hearing-scenarios.json`）        | 運用者       | 製品のシナリオカタログだけ   | ヒアリングの記録 → 台帳                  | ミッション起票・業務の棚卸し | なし               |
| 決定台帳のヒアリング（SSOD）                                     | 運用者       | 案件の未決事項から自動で作る | 決定台帳                                 | 台帳の昇格                   | 件数だけ           |
| 顧客チャネルの `requirements_hearing`、`meeting:hearing_session` | 顧客・誰でも | なし（会話ごとに生成）       | 商談の `requirements.json`、出力ファイル | なし                         | なし               |

PR #1469 は、これらとつながらない 5 つ目の形（`hearing-agenda.schema.json` と、ゴールをパイプラインに直書きしたワークフロー）を足そうとしていた。

求められているのは次の 4 点である。

1. ヒアリングのゴールはテナントが設定する。
2. 答える人がストレスなく進められる。
3. 回答が次の作業に適切に結び付く。
4. 内容を統計として分析できる。

## 方針（判断済み）

- **ヒアリングを 1 つの概念として定義する**。テナントが設定した目的に向けて、人から構造化された回答を集め、決定台帳に記録する。定義（テンプレート）・見せ方（フォーム・対話・アバター）・回答の記録は分ける。
- **背骨は顧客の決定ヒアリングにする**。承認と内容ハッシュによる版の固定、社外の入口、台帳への記録がすでにある。回答の保存先は新しく作らない。
- **見せ方は定義の外に置く**。対話やアバターは、同じ定義の別の見せ方として足す（HR-05）。PR #1469 の画面スポットライト・表情・候補の返答は、そこで項目ごとの任意のヒントとして入れる。
- **PR #1469 から取り込むのは 1 点だけ**。`meeting:hearing_session` が使っている `context` 引数の宣言漏れの修正（`op-catalog.ts` と `actuator-op-discovery.json`）。

## 項目

| ID    | 内容                                                                                                                                                                                                                                                                                                                                                                             | 状況 |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| HR-01 | **テナントのテンプレートと目的、概念の登録**。テナントのテンプレートを `knowledge/confidential/<tenant>/decisions/_templates/` に置き、同じ id の製品テンプレートより優先する。文面は ja / en を直接書ける。テンプレートと調整セットに `objective`（目的と完了の目安）を足し、顧客の画面の冒頭に出し、内容ハッシュに入れる。`hearing` を concept-registry・GLOSSARY に登録する。 | 完了 |
| HR-02 | **回答 → 次の作業の型付きの対応**。テンプレートの項目ごとに `on_answer`（回答の条件と行き先）を持たせる。行き先は既存の governed な先（バックログの WorkItem、担当者への引き継ぎ）に限る。今の種類ごとに決まった振り分け（`bolt-review.ts`・`operator-handoff.ts`）を一般化する。まだ誰も読んでいない brief 入力（`readBriefInput`）もつなぐ。                                   | 予定 |
| HR-03 | **答える人の体験**（customer-room）。途中保存と再開、「わからない / 後で」の明示的な回答、項目ごとの必須、所要時間の目安、条件付きの項目。                                                                                                                                                                                                                                       | 予定 |
| HR-04 | **集計**。学習レポートに、項目ごとの回答の分布、完了率、回答までの時間、どの項目で止まったかを足す。今と同じく件数だけで、顧客の文面は出さない。                                                                                                                                                                                                                                 | 予定 |
| HR-05 | **対話・アバターの見せ方と、ほかの入口の合流**。項目ごとの任意のヒント（画面のスポットライト、表情、候補の返答）を同じ定義に足す。Front Desk のシナリオカタログと `meeting:hearing_session` を同じ定義に寄せる。                                                                                                                                                                 | 予定 |

## HR-01 の実装（2026-11-13）

- 置き場: `decisions/_templates/<template_id>.json`。`_reports/` と同じく、先頭の `_` は案件 id の文法の外なので案件として一覧に出ず、案件と同じ tier・テナントの範囲・`decision_ledger` 権限・バックアップ・オフボーディングに入る。
- 書き込みは `pnpm kyberion customer-decision template put --tenant <t> --file <path> --by user:<member>` だけ。schema で検証し、束縛されたテナントと違う `--tenant` は断り、監査に id と件数だけを残す。`bolt-review` は製品専用で、テナントは書けず、上書きもできない。
- `put` に承認は付けない。テンプレートはそれだけでは顧客に見えない。テンプレートから作った調整セットが顧客に届くのは `submit` がその内容ハッシュを承認した後で、テンプレートを変えても既存の調整セットは変わらない。
- 読み込み: `draft --template <id>` はテナントのテンプレートを先に使う。テナントのテンプレートは毎回読み直し、キャッシュしない（別のテナントに渡らない）。`learning` も同じテンプレートから組織の既定値を読む。
- 文面: 製品テンプレートは語彙のキー、テナントのテンプレートは `{ja, en}` の直書き。1 つの欄にはどちらか一方だけ。調整セットの言語の文面がなければ `[CUSTOMER_DECISION_TEMPLATE_LOCALE_MISSING]` で断り、別の言語やキーを出さない。
- 目的: テンプレートの `objective`、または `draft --objective <text>`（`none` で消す、`--file` でも渡せる）。設定したときだけ内容ハッシュに入るので、目的のない既存の調整セットのハッシュは変わらない。運用者向けの一覧と案件の詳細には目的の文面を出さない（今までどおり id と件数だけ）。
- 主なコード: `libs/core/customer-decision/{template,store,model,hash}.ts`、`scripts/customer-decision/templates.ts`、`presence/displays/customer-room/src/app/main.ts`、`customer-decision-{template,agenda}.schema.json`。
- テスト: `libs/core/customer-decision/template-tenant.test.ts`（解決の順、テナント間の分離、`bolt-review`、文面の形、言語の欠け、ハッシュ）、`scripts/customer_decision.templates.boundary.test.ts`（実パスでの put / list / show / draft、束縛されたテナント）、`scripts/customer_decision.test.ts`（`--objective` と顧客の `view`）。
