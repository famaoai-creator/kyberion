# Surfaces 再設計 — 「個人」と「組織」の定義から作り直す

## 1. 問題の見立て

Surfaces に足りない機能が次々に指摘されるのは、機能が足りないからではなく、
**「誰のための機能か」が定義されていない**ためと考える。定義がないので、機能を足す場所が決まらず、
足すたびに別の面が膨らむ。

現状で確認できた混線は次のとおり。

| #   | 混線                                                                                                                                       | 根拠                                                                                                                        |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 1   | オンボーディングが **運用者(operator)向けの一本道**。個人で使う人、組織に招待された人、組織を立ち上げる管理者が同じ手順書(Step 0〜9)を通る | `onboarding-flow.md` は個人=ルート1、AI会社=ルート2、既存テナント追加=ルート3。「招待されて参加するメンバー」のルートが無い |
| 2   | **組織のメンバー情報が personal tier にある**                                                                                              | `member-registry` は `knowledge/personal/members/{id}.json`。組織の名簿が個人の領域にある                                   |
| 3   | concierge が「CEO 秘書」で、**個人の秘書と組織の承認キューを兼ねる**                                                                       | `SURFACES.md`。「決める」は個人の判断か組織の判断か区別されない                                                             |
| 4   | **外部サービス連携の持ち主が不明**。連携の登録は「サービス連携」1 画面で、個人の Gmail と組織の Slack が同じ扱い                           | `settings > サービス連携`、service catalog はサービス単位で持ち主の概念が無い(未確認部分あり)                               |
| 5   | 3 つの名前(`customer_slug` / `tenant_slug` / `organization_id`)を人が理解する必要がある                                                    | `onboarding-flow.md` §2                                                                                                     |
| 6   | 面が 5 つ + pad 10 + チャネル 4 で、入口が散在                                                                                             | `SURFACES.md`                                                                                                               |

## 2. 再定義 — 誰が何をするか

### 2.1 二つの主体(actor)

|                | **個人 (Person)**                                                                            | **組織 (Organization)**                                                                    |
| -------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 本質           | 自分の時間・注意・記憶・判断を持つ人間                                                       | 複数の人と agent が共有する目的・責任・権限・予算                                          |
| 所有するもの   | 自分の identity、好み、記憶、個人の連携(自分の Gmail/カレンダー)、通知の受け方、自律度の好み | メンバー名簿、ロール、テナント境界、共有の連携(Slack workspace、Git)、予算、ポリシー、監査 |
| 決めること     | 自分の仕事の進め方、自分の分の承認、自分のデータの公開範囲                                   | 誰が何をできるか、何を自動化してよいか、いくら使うか、何を記録するか                       |
| データの置き場 | personal tier(本人のみ)                                                                      | tenant scope(組織のメンバーが権限に応じて)                                                 |
| 責任の帰属     | 本人                                                                                         | 組織のオーナー(人間)                                                                       |

### 2.2 一人の人間が持つ二つの顔

同じ人が「個人としての私」と「組織 A のメンバーとしての私」を持つ。これを **1 つの Person に N 個の Membership** として表す。

```text
Person(personal tier: 本人だけが読める)
  ├─ Personal space  … 自分の連携・記憶・好み
  └─ Membership × N  … 組織ごとのロール(owner / approver / operator / viewer)
                        ※ 組織側の名簿(Roster)は組織の tenant に置き、Person からは参照のみ
```

原則:

1. **個人のデータは組織に渡らない。** 組織が見られるのは、本人が組織のために行った行為(承認、作業、成果物)だけ。
2. **組織のデータは、退職・脱退しても組織に残る。** 個人の記憶は本人に残る。
3. **連携は必ず持ち主が一人(人または組織)。** 持ち主のいない連携は作れない。
4. **承認は「誰の権限で」を明示する。** 承認画面に「あなたの個人の判断」か「組織 X の承認者として」かを常に表示する。

### 2.3 三つのオンボーディング(別物にする)

|                             | 対象                   | ゴール                                                              | 所要                  | 現状                                       |
| --------------------------- | ---------------------- | ------------------------------------------------------------------- | --------------------- | ------------------------------------------ |
| **P. 個人オンボーディング** | 自分で使い始める人     | 名前・好み・連携 1 つ・最初の依頼が動く                             | 10 分以内             | ルート1。CLI 前提で GUI が薄い             |
| **J. 参加オンボーディング** | 招待されて組織に入る人 | 招待受諾 → ロール確認 → 見える範囲の説明 → 個人の設定               | 5 分以内              | **無い**                                   |
| **O. 組織立ち上げ**         | 管理者・オーナー       | tenant 作成 → メンバー招待 → 共有連携 → ポリシーと予算 → activation | 30 分以内(ウィザード) | ルート2・3。コマンド列で、招待の概念が無い |

P と J は**環境構築(Step 1〜2)を含まない**。環境構築は「運用者(operator)」の仕事として切り離し、
利用者には見せない(管理者・self-host 運用者向けの別ページ)。

### 2.4 連携システムの分類

| 種別         | 持ち主         | 例                                                      | 資格情報                             | 承認者         |
| ------------ | -------------- | ------------------------------------------------------- | ------------------------------------ | -------------- |
| **個人連携** | Person         | 自分の Gmail、カレンダー、iMessage、Telegram の個人 bot | 本人の OAuth。本人のみ取消可         | 本人           |
| **組織連携** | Organization   | Slack workspace、GitHub org、Jira、共有の Drive         | 組織の secret。オーナー/管理者が管理 | 組織のオーナー |
| **実行基盤** | Operator(環境) | reasoning backend、ComfyUI、Whisper                     | 環境の設定                           | 運用者         |

面の見せ方は、個人は「設定 > 自分の連携」、組織は「組織 > 連携」の二か所に分け、
各連携に **持ち主バッジ・最終確認日時・接続の健全性** を出す。実行基盤は管理画面に隠す。

## 3. 面の再編案

面を増やさず、**主体で切る**。

| 面            | 主体        | 役割                                                             | 現在の対応                                                   |
| ------------- | ----------- | ---------------------------------------------------------------- | ------------------------------------------------------------ |
| **Me(私)**    | 個人        | 今日のブリーフィング、頼む、自分宛の判断、自分の連携・記憶・通知 | presence-studio + concierge の個人側                         |
| **Org(組織)** | 組織        | 組織の判断キュー、進み具合、メンバー、連携、予算、ポリシー       | concierge の組織側 + chronos の一部                          |
| **Ops(運用)** | 運用者/監査 | 監視、介入、監査、環境設定                                       | chronos + operator-surface + computer-surface を段階的に統合 |

- 共有レール(ホーム/頼む/決める/進み具合/設定)は残す。ただし画面上部に **コンテキストスイッチャー**(個人 / 組織 A / 組織 B)を置き、切り替えると同じレールが別の主体を表示する。
- 「決める」は、個人の判断と組織の承認を**同じ一覧に混ぜるが、必ず主体ラベルを付ける**。
- pad は Me の「取り込み」に統合し、個別ポートを廃止する(段階移行)。

## 4. 「足りない機能」の再配置

先の指摘(O1〜O12 / P1〜P12)は、この定義に沿って所属が決まる。

| 主体 | 機能                                                                                                                                     |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Me   | P1 PWA/Web Push、P2 通知設定、P3 検索、P4 履歴、P5 パスキー、P6 カレンダー、P7 個人の自律度、P8 モバイル取り込み、P9 データ管理権        |
| Org  | O1 SAML/SCIM、O4 予算、O5 委任・代理、O6 ポリシー編集、O7 共同レビュー、O8 メンバー管理、O9 テナント運用、O11 Teams 等、O12 外部ポータル |
| Ops  | O2 監査エクスポート、O3 横断ダッシュボード、O10 ステータス                                                                               |

新しい機能は「Me / Org / Ops のどれか」が決まらない限り着手しない、を受け入れ条件にする。

## 6. 既存ルールとの関係(意図的に外すもの)

ユーザーの指示により、次は本計画の中では前提にしない。実装段階で改めて可否を判断する。

- 「5 つの UI サーフェス」という面の数と、`surface-roles.json` の 1 面 1 役割
- `onboarding-flow.md` の 3 ルート構成
- personal tier に member を置く現在の配置

**守るもの**(緩めない): tier/tenant の漏洩防止、server-side での viewer 解決、secure-io、承認ゲート。
これらは主体モデルの前提であり、再設計の目的そのものである。

## 7. 決定事項(2026-09-30 オーナー回答)

前提: オーナーは多数の会社を兼務しており、「自分の仕事を全部任せられる仕組み」としてこのハーネスを作っている。
したがって複数組織の兼務は**例外ではなく主要ユースケース**である。人が段階を踏んで確認する運用は取らず、依存関係の順に一括で実装する。

| #   | 決定                                                                                                                                                                                                                                          | 理由                                                                                                                                                                                     |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Ops は日常の面として持たない。** 面は **Me / Org** の 2 つ。運用の情報は「例外」として Me に上がり、根拠は各項目の「根拠を見る」(inspect)で開く。監視盤(chronos 等)は運用者・監査向けの管理コンソールに降格し、日常のナビゲーションから外す | プロダクトの目的は「人が判断だけをする」こと。監視の面が独立すると、人が見張る運用を誘発する。うまく回る状態とは、人が見に行かなくても例外だけが届く状態である                           |
| 2   | **Actor は Kyberion が保持する(人・エージェント・サービス共通)。** 外部 IdP は認証(本人確認)の錨に限り、権限・所属・委任は Kyberion の Actor registry が正本                                                                                  | 協調する主体に人間とエージェントが混在する。権限の正本が IdP にあると、エージェントを同じ枠で扱えない。`libs/core/actor.ts`(human / agent / service)が既にあり、その上に registry を作る |
| 3   | **複数組織の兼務を前提にする。** 一人の Person が N 個の Membership を持つ。Me は全組織の判断を横断して集約するが、**組織間の情報は混ぜない**(組織ごとに文脈を分離し、Me には判断に必要な最小の要約だけを渡す)                                | 兼務では、A 社の情報が B 社の判断や成果物に漏れることが最大のリスクになる                                                                                                                |
| 4   | **人向けの段階分けはしない。** 技術的な依存順(データ→認可→招待→UI)でだけ順序を付ける                                                                                                                                                          | §8 参照                                                                                                                                                                                  |

### 決定 2 の補足: 人間しか決められない原則との関係

`actor.ts` は「承認・却下は人間のみ」を原則にしている。これは維持する。ただし**人が事前に委任した範囲内で、エージェントが人の名で決める**ことは許す。
記録は `actor = agent`、`on_behalf_of = user:<member>`、委任の根拠(autonomy policy の該当ルール)を必ず残す。責任は常に委任した人間に帰属する。
委任の範囲外(外部公開、機密、予算超過、ガバナンス変更、取消不能な操作)は人に上がる。

### 決定 4 の補足: 段階を踏むことに、人の不安解消以外の利点はあるか

あるのは次の 2 点だけで、いずれも「人に確認を取る段階」ではなく、実装側で解消できる。

1. **不可逆な移行(名簿の置き場所の変更)**。→ 段階分けではなく、dry-run・バックアップ・ロールバックを最初から実装して一括で行う。
2. **実利用での使い勝手の検証**。→ 完成後に使ってもらう。途中の承認ゲートにはしない。

人にしか用意できないもの(実際の IdP 設定、本番の secret、実在する顧客の同意)は、必要になった時点で個別に依頼する。

## 8. 確認できていないこと

- 連携の持ち主が現在どこにも保存されていないか(catalog が 4 件のみで、実際の登録状況は未確認)。
- Roster を tenant へ移す影響範囲(member-registry の参照箇所)。
- chronos / operator-surface / computer-surface の統合コスト。
