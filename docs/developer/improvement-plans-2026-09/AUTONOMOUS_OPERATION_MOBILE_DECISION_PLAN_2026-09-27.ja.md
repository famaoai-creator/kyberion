# 自律運用とスマホ決裁

## 判断

オペレーターがターミナルに張り付かなくても、エージェント同士が相互に補い合って作業を進められるようにする。
人の関与は「本当に重要な判断」に絞り、スマホ(Telegram / Slack)から非同期に決裁する。

現在人が必要になっている場面は主に3つある。

1. 上流の計画(ミッションの目的・範囲・成功条件の合意)
2. PR の承認(CI 待ち、レビュー、マージ)
3. コンフリクトの対処

これらを、別の提供元のエージェントによる相互チェック、リスクに応じた段階的な権限、元に戻せる仕組みで補う。
人の関与をゼロにすることは目標にしない。目標は「重要な判断だけを、1日数回スマホで行う」ことである。

## 原則

1. **判断の権限を明文化する。** すべての判断を `auto`(自動で実行)/ `notify`(実行して事後通知)/ `approve`(人が承認)の3段階に分ける。
   段階は既存の `autonomous-ops-policy.json` の4軸(scope / reversibility / sensitivity / confidence)で点数化して決める。
2. **人の代わりに、別の提供元のエージェントが相互チェックする。** 書いたエージェントとは別の提供元がレビューし、テストと合わせて確認する。
   提供元を分けることで、同じ誤りを見逃す可能性を下げる。
3. **待たずに進める。** 承認待ちの作業は一時停止し、その間は他の作業を進める。人への確認はダイジェストにまとめ、緊急のものだけ即時通知する。
4. **元に戻せるものは自動、戻せないものは人。** 自動マージした PR は自動で取り消せるようにする。
   取り消しが効かない操作(外部公開、機密データ、ガバナンス変更、予算超過)だけを人に上げる。
5. **任せる範囲は実績で広げる。** 自律度はプロジェクトごとに段階設定し、取り消し率と人による判断の覆し率で引き上げ・引き下げを行う。

## 不足している部分

- ミッション・PR・コンフリクトの判断に対する権限の定義(リスク点数化の対象外)
- CI の監視と自動修正、自動マージ、マージキュー
- GitHub 上の PR に対する別提供元のレビュー(現在はミッション内の `review-task` のみ)

- 決裁内容を1枚にまとめる形式(決裁カード)とダイジェスト

## 判断権限の初期マトリクス

オペレーターの選択(2026-09-27)に基づき、低リスクは自動、中リスクは拒否できる猶予時間の後に自動、高リスクは人の承認とする。

| 判断                   | 低リスク                                      | 中リスク                                             | 高リスク |
| ---------------------- | --------------------------------------------- | ---------------------------------------------------- | -------- |
| 計画(ミッションの開始) | 包括委任の範囲内なら自動                      | 決裁カードを通知し、猶予時間内に拒否がなければ開始   | 人の承認 |
| PR のマージ            | CI 合格 + 別提供元の承認で自動マージ          | 同上 + 猶予時間後に自動マージ                        | 人の承認 |
| コンフリクトの解決     | 機械的な解決 + テスト合格で自動               | 解決案 + テスト + 別提供元の承認で、猶予時間後に自動 | 人の承認 |
| 細かい質問             | 別エージェントに相談し、`knowledge/` から回答 | ダイジェストで事後報告                               | 人に質問 |

高リスクの例: `governance/`、`secure-io`、スキーマ、認証・認可、テナント境界、外部公開、依存関係のメジャー更新、予算超過、自動修正の上限到達。

## ワークストリーム

### A. スマホ決裁の基盤

- **決裁カード**の形式を定義する。項目は、何を決めてほしいか、推奨案、リスク段階と理由、元に戻せるか、期限、証跡へのリンク。
  ボタンは「承認」「修正を指示」「却下」「理由を聞く」の4つ。承認の正本は `approval-store` とし、カードは表示にすぎない。
- **猶予時間**: 中リスクの操作は、通知から一定時間拒否がなければ実行する。期限と拒否の結果は `approval-store` に記録する。
- **ダイジェスト**: 朝と夕に、自動で実行したこと、猶予時間中のもの、判断待ちのものをまとめて送る。
- **全停止**: スマホからの1コマンドで `kill-switch` を発動し、全エージェントの書き込みを止める。
- **本人確認の強さをリスクに合わせる**: 中リスクまではチャットのセッション(`surface_session`)で可。高リスクは後の段階でパスキーを必須にする。

### B. PR の自律化

- **CI の監視と自動修正**: PR の CI を監視し、失敗したら原因を分類して修正する。修正回数には上限を設ける。
- **別提供元のレビュー**: PR の作成者とは別の提供元のエージェントがレビューし、結果を PR と証跡に残す。
- **差分のリスク点数化**: 変更されたパス、差分の規模、テストの増減から、リスク段階を決める。
- **マージキューと自動マージ**: 段階ごとの規則に従ってマージする。マージ後に `main` の CI が失敗した場合は自動で revert の PR を作る。

### C. コンフリクトの自律化

- **検出**: 開いている PR を定期的に `main` と突き合わせ、コンフリクトを早期に見つける。
- **機械的な解決**: ロックファイル、生成物、インポートの並びなどは、作り直してテストする。
- **意味的な解決**: 両方の PR の説明と差分から意図を読み、解決役のエージェントが案を作る。テストと別提供元のレビューで検証する。
- **予防**: 担当するファイル範囲を `work-coordination` のクレームとして宣言し、同じ範囲の同時編集を減らす。

### D. 上流計画の委任

- **包括委任**: 事前に承認した作業の種類(テスト強化、リファクタ、ドキュメントなど)と予算の範囲内なら、計画の承認ゲートを自動で通す。
- **計画パネル**: 計画役が案を作り、反論役とレビュー役が意見を付けて、1枚の決裁カードにまとめる。
- **相談の自己解決**: 細かい質問は、まず別のエージェントに相談して `knowledge/` から答えを探す。解決しないときだけ人に上げる。

### E. 実績による段階的な引き上げ

- 自律度をプロジェクトごとに L0(すべて人が承認)から L4(高リスクのみ人が承認)まで設定する。初期値は L1 とする。
- 指標: 自動マージ後の revert 率、人が判断を覆した率、猶予時間中の拒否率、人への問い合わせ件数と応答時間。
- 高リスク承認のためのパスキー(WebAuthn)PWA を実装する。

## P0 の結果(2026-09-27)

ミッション `MSN-AUTONOMOUS-MOBILE-DECISION-20260927` で、人の介入を集計する `scripts/report_human_interventions.ts` を実装した(実行: `node dist/scripts/report_human_interventions.js [--since YYYY-MM-DD] [--json]`)。
情報源は承認ストア、git 履歴(PR マージと、`main` 取り込み時のコンフリクトの再現)、ミッション状態の3つである。

2026-08-28 以降の30日間の集計:

| 種類             | 件数 | 内訳                                                           |
| ---------------- | ---- | -------------------------------------------------------------- |
| PR のマージ      | 92   | すべてオペレーターの手動マージ(1日約3件)                       |
| 計画             | 18   | 16件は計画中のまま止まっているミッション                       |
| コンフリクト     | 2    | `main` 取り込み22件のうち、実際にコンフリクトしたのは2件(約9%) |
| 秘密情報         | 33   | 22件はポリシーによる自動承認、11件は放置された承認待ち         |
| ミッションの操作 | 7    | 一時停止のまま止まっているミッション                           |

分かったこと:

1. **最大の負荷は PR のマージ**である。P2(PR の自律化)の効果が最も大きい。
2. **23件のミッションが、誰にも通知されずに人を待っている**(最も古いものは 2026-07-26)。P1 のダイジェストに「止まっている待ち」を含める。
3. **コンフリクトは少ない**。`main` の取り込みの大半は機械的に済むため、P3 はクリーンな取り込みの自動化から始める。
4. **承認ストアは、いまのところ人の判断の記録として使えない**。記録の95%以上(3,351件)はテストが本番の承認ストアに書き込んだもので、ポリシーの自動承認が人の判断として記録され、承認待ちに期限がない。実際の人の判断(PR マージ、計画の合意)は GitHub とチャットで行われ、承認ストアを通っていない。

## 判断権限マトリクス 第2版(2026-09-27 オペレーター承認済み)

反論役のレビューを受けて、初期マトリクスを次のように改めた。詳細はミッション証跡の `decision-rights-matrix-proposal.json` にある。

- **段階は実行するエージェントではなくゲートが決める。** 変更されたパス、テストの変更、依存関係、対象ティアとテナントから計算する。エージェントは段階を上げることはできるが、下げることはできない。
- **どれか1つの軸が最大なら人の承認。** 取り消しにくい操作は少なくとも事後通知にする。秘密情報、外部公開、テナントをまたぐ操作、下位ティアへの書き込み、ガバナンス変更、依存関係のメジャー更新は常に人の承認とする。
- **高リスクのパスを広げる。** 承認・権限・テナント・パス解決のモジュール、CI・依存関係・設定、テストの許可リスト、Telegram / Slack のブリッジ、この集計スクリプト自体を含める。新しいセキュリティ関連モジュールが漏れたら失敗する契約テストを追加する。
- **別提供元のレビューは、オーケストレーターが選ぶ。** 別のモデルで、差分だけを見てレビューし、レビューはマージ対象のコミットに結び付ける。
- **猶予時間は安全側に倒す。** 通知の到達を確認してから数え始め、活動時間外は止める。到達を確認できなければ人の承認に切り替える。パスキーができるまで、チャットでの承認は取り消せる操作に限る。
- **CI の自動修正がテストを弱めたら人の承認。** テストの削除・スキップ、スナップショットの更新、設定の変更が該当する。
- **いきなり有効にしない。** 2〜4週間は「実行したらどうなったか」だけを記録し、オペレーターの実際の判断との一致率を確認してから有効にする。

### P1-1〜P1-4 の実装(2026-09-27、ミッション `MSN-APPROVAL-STORE-HYGIENE-20260927`)

- **P1-1(実装済み)** 承認ストアのパスを `approvalStoreRoots()` に集約した。vitest の実行中は `active/shared/runtime/vitest-approvals/` に書く。この場所は保存期間カタログで1日後に消える。本番の場所に書かないことを `approval-store.test.ts` の契約テストで確認している。
- **P1-2(掃除の処理は実装済み、本番への適用は未実施)** `node dist/scripts/approval_store_hygiene.js` で確認できる。既定は dry-run で、`--apply` を付けると `active/archive/.trash/` へ移す。移した記録は30日間復元できる。判定規則は集計スクリプトと共通(`libs/core/approval-store-hygiene.ts`)。2026-09-27 の dry-run では、本番の記録 3,086 件のうち 3,081 件がテスト由来だった。残る実際の判断は5件(計画承認3件、project-trust 2件)。P0 で「放置された秘密情報の申請」とした11件も、`secret-introduction.test.ts` の残骸だった。ごみ箱に書けるのは sovereign ペルソナだけなので、`--apply` は `KYBERION_PERSONA=sovereign node dist/scripts/approval_store_hygiene.js --apply` で実行する。ペルソナがないと、何も変更せずに実行すべきコマンドを表示して終了する。
- **P1-3(実装済み)** 秘密情報のポリシー自動承認は `decidedBy: policy:secret-introduction-local-low-risk`、`decidedByType: service` で記録する(スキーマの非人間の値は `service` / `ai_agent`)。依頼した人は note に残す。
- **P1-4(期限切れは実装済み、ダイジェストへの掲載は P1-8)** 秘密情報の申請は作成から24時間で期限切れにする。掃除の処理は、`expiresAt` を過ぎた申請と、期限なしで14日を超えて放置された申請を、承認ストアの正規の遷移で `expired` にする。イベントには `reason` を記録する。定期実行への組み込みは未実施。

### P1-5 の実装(2026-09-27、ミッション `MSN-AUTONOMY-GATE-MATRIX-20260927`)

- **P1-5(実装済み)** `autonomous-ops-policy.json` を 1.1.0 にし、第2版の行動13件、`high_risk_paths`、`never_auto`、`active_hours`(09:00〜22:00、Asia/Tokyo)を追加した。行動ごとに `action_class`、`veto_window_minutes`、`max_attempts`、`required_evidence` を持てる。
- ゲートは点数による段階に、次の規則で段階を上げる。上げた規則は結果の `escalations` に残る。
  - 変更に `high_risk_paths` の該当があれば承認。リポジトリ外を指すパスも承認。
  - `never_auto` の種類(行動の種類、または呼び出し側が検出した種類)なら承認。
  - どれかの軸が3なら承認。取り消しやすさが2以上なら少なくとも通知。
  - エージェントは `requestedDecision` で段階を上げられるが、下げられない。
  - テナントの上書きは下限としてだけ効く(軸の点数は高い方、予算の上限は低い方)。
- パスの照合は大文字と小文字を区別しない。ドライブ名付きのパスもリポジトリ外として扱う。テナントの上書きで、基本のポリシーにない行動は作れない。
- 呼び出し側は `decision` ではなく `allowed` で実行を判断する(`auto_checkpoint`、`daemon_watchdog`)。
- 第2版の行動はすべて試行モード(`shadow: true`)で登録した。ゲートは段階を計算するが、`allowed` は常に `false`。既存の6行動の判定は変わらない。
- `tests/autonomous-ops-high-risk-coverage-contract.test.ts` は、名前が承認・権限・テナント・秘密情報などに当たる `libs/core` のモジュールが `high_risk_paths` に含まれることを確認する。新しいモジュールは一覧に加えるまでテストが失敗する。

### P1-6〜P1-8 の実装(2026-09-28)

人の関与を「いつ・何を・何もしなければどうなるか」で一意に伝えるため、判断の粒度を4段階に固定し、決裁カード・拒否期間・ダイジェストを1つの流れにまとめた。運用の約束は `knowledge/product/orchestration/hitl-decision-loop.md` にある。

**関与の4段階(ゲートが決め、エージェントは下げられない)**

| 段階     | ゲート                         | エージェント             | 人                                       | スマホが鳴るか                  |
| -------- | ------------------------------ | ------------------------ | ---------------------------------------- | ------------------------------- |
| `none`   | auto                           | そのまま実行             | 何もしない。ダイジェストに載る           | 鳴らない                        |
| `fyi`    | notify                         | そのまま実行             | 何もしない。ダイジェストに載る           | 鳴らない                        |
| `veto`   | notify + `veto_window_minutes` | 保留して他の作業を続ける | 反対するときだけ操作する                 | カード送信時に1回               |
| `decide` | approve                        | 保留して他の作業を続ける | 判断する。判断まで止まり、期限で取り下げ | 1回(急がない質問はダイジェスト) |

スマホが鳴るのは「あなたが止めている」か「異議の締め切りが動き出した」ときだけにした。催促はダイジェストで行い、通知を繰り返さない。

- **P1-6(実装済み)決裁カード** 保存する形は下の `MSN-DECISION-CARD-20260928` の `DecisionCard`(`libs/core/decision-card.ts`)に一本化し、関与の段階・試行モード・時間帯・届け先を足した。表示は `libs/core/approval-decision-card.ts` が担い、どの面でも同じ順で出す: 段階 → 決めてほしいこと → 推奨 → 人が必要な理由(ゲートの `escalations` を文章化し、全件) → 取り消せるか → 何もしない場合 → 証跡 → 返信方法。返信は `承認` / `却下`・`異議` / `appr:<id>:changes <指示>`(`revise` も可) / `appr:<id>:explain`。拒否期間付きのカードでは、ボタンが「今すぐ進める」「止める(異議)」になる。自律運用のカードは届けた面とチャットからの返信だけを受け付ける。
- **P1-7(実装済み)拒否期間** `libs/core/approval-veto-window.ts`。ブリッジが実際に送れたとき(`drainSurfaceOutbox` の成功)に時計を始め、活動時間内の分だけ数える。30分以内に届かなければ恒久的に `decide` に切り替わり、遅れて届いても自動では進まない。期限が来たものは `policy:veto-window`(`decidedByType: service`)として承認し、人の判断としては記録しない。拒否期間付きの申請に `human_only` は付けられない。試行モードは「進んだはず」を記録するだけで、人の判断を待つ。
- **P1-8(実装済み)ダイジェスト** `libs/core/approval-digest.ts` と `scripts/approval_inbox.ts`。先頭の1行で「あなたの判断 N件・異議がなければ進むもの M件・自動で済ませたこと K件」を示し、その下に、判断待ち(古い順)、進行予定(期限の近い順)、3日以上止まっているミッション、自動で済ませたこと、期限切れを並べる。`none` / `fyi` は承認記録を作らないため、実行記録(notice)として残してダイジェストに載せる。通知先は `per_event.decision_digest`。
- **呼び出し口** `routeAutonomousDecision()`(`libs/core/approval-decision-routing.ts`)。エージェントはゲートの結果を渡すだけで、実行してよいか(`proceed`)、保留して他の作業へ進むか(`parked`)が返る。カード作成、拒否期間、通知、実行記録はこの関数が行う。

## 評価(2026-09-28): 持続的な自律運用に向けて

判断の粒度と人への伝え方は、上の4段階とカードで一本化できた。持続運用のために残っている穴は次のとおり。

1. **定期実行への組み込み**: `approval_inbox.js tick`(数分ごと)と `digest --send`(朝夕)、`approval_store_hygiene.js --apply` を chronos のスケジュールに載せる。載るまでは拒否期間が進まない。
2. **呼び出し側の移行**: P2 以降の行動(PR マージ、コンフリクト解決、ミッション開始)は `routeAutonomousDecision()` を経由させる。既存の `mission-alignment-gate`、`background-review`、秘密情報の申請にも `decisionCard` を付けると、全ての判断が同じカードで届く。
3. **ネイティブボタン**: Telegram / Slack は4つのボタンを持つ。自律運用のカードは通知の送信箱(outbox)経由で届くため、まだボタンが付かず文字で返信する。送信箱にボタンを載せ、Discord も揃える。
4. **スマホからの全停止(P1-9)** と **試行モードの一致率(P1-10)**: 拒否期間の試行記録(`veto_window_elapsed_shadow`)と人の実際の判断を突き合わせる集計を `report_human_interventions` に足す。
5. **相談の自己解決**: `decide` を上げる前に別の提供元のエージェントと `knowledge/` に当たる手順を、ルーティングの前段として実装する(計画 D)。

### P1-6 の実装(2026-09-28、ミッション `MSN-DECISION-CARD-20260928`)

- **P1-6(実装済み)** 決裁カード(`libs/core/decision-card.ts`)は、判断すること、推奨、段階と理由、取り消せるか、期限、証跡を1画面にまとめる。承認要求に `decisionCard` として保存し、作成時に検証する。証跡は `https://` の URL かリポジトリ内の相対パスだけを受け付ける。
- `buildDecisionCard` はゲートの結果からカードを作る。段階はゲートと呼び出し側の厳しい方、取り消せるかは両方が「できる」ときだけ「できる」。ゲートの理由を加え、試行モードの注記は除く。長すぎる理由は切り詰める。
- カードは秘密情報の登録・ローテーションの申請と、ミッション計画の承認(アラインメント)に付く。PR のマージなどは試行モードのまま。
- Telegram と Slack は、カードのある承認要求に4つのボタン(承認・修正を指示・却下・理由を聞く)を出す。カードのない要求は従来どおり承認と却下の2つ。
  - 「修正を指示」は却下として記録し、指示の本文を `changeRequest` に残す(1〜2000文字)。新しい状態は作らない。エージェントは指示に沿って修正したカードを出し直す。Telegram は返信を促すメッセージへの返信で、Slack はモーダルで指示を受け取る。
  - 「理由を聞く」はカードと申請に保存した理由だけを返し、要求は保留のまま。モデルは呼ばない。
  - どちらも、要求と同じチャンネル・スレッドからの操作だけを受け付け、送信者の許可一覧を確認する。
- 未実施: 秘密情報とアラインメントの承認要求は `terminal` / `brief` のチャンネルにあるため、Telegram と Slack へ届ける経路は別途必要。停止スイッチ(P1-9)。拒否期間(P1-7)とダイジェスト(P1-8)は上の節で実装した。
- 上の P1-6〜P1-8 の節と統合した(2026-09-28)。カードの見出しは段階で出し分け、「何もしない場合」を必ず表示する。ゲートの理由は内部の文字列ではなく、言い換えた文で全件出す。

## 安全策

- 取り消せない操作は、段階に関係なく人の承認を必須にする。
- 予算(トークン、費用、時間)の上限を超える前に止まり、決裁カードを出す。
- 自動修正と自動解決には回数の上限を設け、上限に達したら人に上げる。同じ内容の再試行はしない。
- すべての自動判断は `approval-store` と証跡に記録し、ダイジェストで事後に確認できるようにする。
- マージ後の失敗は自動で revert の PR を作り、自律度を1段階下げる。
