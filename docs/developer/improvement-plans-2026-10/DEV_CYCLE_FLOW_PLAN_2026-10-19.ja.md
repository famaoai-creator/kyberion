# 開発サイクル流量改善計画 (2026-10-19)

PR #1156〜#1187（2026-10-18〜19、約 30 件）の CI 結果と中身を分析した結果をもとに、「ローカルでは通るのに CI で落ちる」「1 つ落ちると CI がもう 1 周必要になる」「複数プロバイダーが同じ PR に触る」という摩擦を取り除く。

## 観測結果

| 失敗の種類                     | 件数                                 | 例                                                                                          |
| ------------------------------ | ------------------------------------ | ------------------------------------------------------------------------------------------- |
| 登録・ratchet 漏れ             | 3                                    | #1183 `shared-tmp-ratchet`、#1184 `mission-lookup-boundary` / `governance-rules`            |
| 生成ファイルの更新漏れ         | 2（さらに 3 件は CI 前に手で再生成） | #1182 `op-registry`、#1171 `role-assumption-reachability`                                   |
| タイミング依存・テストの独立性 | 3                                    | `peer-task-exchange`（#1183 と main、#1186 で修正）、#1162、#1153                           |
| OS 固有                        | 3                                    | Windows `ui failed to spawn` のまま #1175・#1176 がマージ、macOS の Codex 中断競合（#1171） |
| lint / 型 / フォーマット       | 0                                    | —                                                                                           |

構造的な原因:

1. `pnpm check -- --scope pr`（48 ゲート）と、CI `lint-and-validate` の `--scope full`（81 ゲート）が一致しない。変更パスごとの例外表は文章だけで、どのツールも読んでいない。
2. `resolve generated` が生成器の一部しか扱わない。コミット前フックで自動実行されるのは knowledge-index だけ。
3. `lint-and-validate` が落ちると `test` / `intent-smoke` / `first-win` がスキップされ、もう 1 周必要になる。
4. Cross-OS の macOS は 16〜19 分（負荷時 30〜40 分）。1 回の push で約 10 回ビルドし、パスによる絞り込みもない。
5. テストに 200ms 以下の実時間 sleep が 37 ファイル・84 箇所ある。リトライや隔離の仕組みはない。
6. `vital-check` が push のたびに同じコメントを投稿する。赤い Windows のままマージできる。
7. クラウドセッションで `dist/` がないと、フックが Bash / Edit をすべて拒否し、ブートストラップ自体を実行できない。
8. 担当プロバイダーが不明確で、他のエージェントの PR を記録なしで修正している（#1182）。

## 施策と実装

| ID                | 施策                                                                                                                                                                                         | 実装 PR |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| S1 / S3 / M1      | `ci-gates.json` に `paths` を追加し、`pnpm check -- --changed` で変更パスに応じたフルスコープゲートを選ぶ。登録系テストのゲート。`pr create` と preflight もこれを使う                       | #1192   |
| S2                | `resolve generated` で全生成器を扱い、`--check` と pre-push フックで検出する                                                                                                                 | #1191   |
| S4 / S5 / S7 / M5 | `test` を `lint-and-validate` から切り離し、各ステップは失敗後も続行。Cross-OS はビルドを再利用し、文書だけの変更では重い OS ジョブを省略。vital コメントは 1 件を更新。`merge_group` に対応 | #1190   |
| S6                | テストの実時間 sleep を増やさない ratchet ゲートを追加し、TTL / 期限に関わる競合を偽装タイマーへ置き換える                                                                                   | #1193   |
| S8                | `dist/` がないときもブートストラップ用コマンドだけを許可し、session-start の失敗を可視化する                                                                                                 | #1189   |
| M2                | エージェントごとの worktree（`pnpm kyberion worktree`）と、その一覧に担当者を表示                                                                                                            | #1194   |
| M3                | 変更要求（PR / MR / ブランチ）の担当を WorkItem の claim に紐付ける。forge 非依存                                                                                                            | #1188   |
| M4                | CI 失敗の分類と次の一手（`ci_failure_triage`）。main が赤くなったら自動で issue を起票                                                                                                       | #1195   |

## マルチモデル運用の型

1. **実装担当**（Claude / Codex / Devin / Gemini）: claim を取り、`pnpm work link-change` で変更要求を紐付けて担当を明示する。並列で作業するときは worktree を分ける（M2）。
2. **事前チェック担当**: push 前に `pnpm kyberion pr preflight` と `resolve generated --check` を実行し、1 回目の CI で通る状態にする（S1 / S2 / S3）。
3. **レビュー担当**: 実装とは別のプロバイダーが、ミッション台帳の review-task（レビュー独立性）を使ってレビューする。
4. **CI 対応担当**: 赤い CI は triage 結果の分類に従って対応する（M4）。他の PR の失敗なら、`pnpm work change-owner` で担当を確認し、修正を移植するか担当者へ引き継ぐ。main の赤は自動起票された issue から修正 PR を出す。

## リポジトリ設定（オーナーが手動で行う）

- 必須チェックに Cross-OS の macOS / Windows ジョブを含める（赤いままのマージを防ぐ）。
- マージキューを有効にする（ワークフロー側は `merge_group` に対応済み）。

## 指標と目標

| 指標                                 | 現状（観測期間）     | P0 後の目標 | P1 後の目標 |
| ------------------------------------ | -------------------- | ----------- | ----------- |
| 1 回目の push で CI が通る PR の割合 | 約 73%               | 90% 以上    | 95% 以上    |
| PR あたりの修正用追加コミット        | 約 0.3               | 0.1 未満    | —           |
| CI の結果が出るまでの時間（PR）      | 約 19 分（Cross-OS） | —           | 12 分以下   |
| 不安定なテストによる失敗             | 週 2 件              | —           | 週 0 件     |
| 赤いチェックのままのマージ           | 2 件                 | 0 件        | 0 件        |

観測期間は 2 日・約 30 PR と短い。マージまでの時間には人の待ち時間も含まれる。各 PR のマージから 2 週間後に、同じ方法で再計測する。
